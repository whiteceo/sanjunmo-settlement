# [AI 에이전트 전용 명세서] AI 에이전틱 개발 · 정합성 검증 환경 구축 (v1.1)

> **문서 용도**: 이 문서는 **AI 에이전트(Claude Code · 안티그래비티)**가 프로젝트 환경을 세팅하거나, 각자의 역할(PO 정본 개정 / 개발자 화면 구현 / 정본↔코드 대조 검수 / 레거시 역공학 문서화 / UIX Figma 연동)을 수행할 때 직접 읽고 따르는 **AI 실행 명세서(Executable Spec)**다.
> 사람(PO · 개발팀 · UIX팀)에게 설명하고 브리핑하기 위한 시각 자료는 동일 폴더의 **`AI_에이전틱_환경_가이드.html`**을 사용한다.

---

## 1. 아키텍처 개요 및 핵심 원칙

### 1.1 왜 이 체계가 필요한가?
1. **작업자별 로컬 AI의 정본 이탈(Drift) 차단**: 여러 개발자가 각자 로컬에서 Claude Code로 코딩할 때, 정본을 안 읽거나 AI가 빈틈을 임의로 추론해 정본과 다른 로직·상태값·코드를 만드는 현상을 막는다.
2. **도메인 간 비즈니스 로직 충돌 방지**: 회원·권리자·정산 ↔ 주문·환불·쿠폰 ↔ 게시판·권한·로그처럼 담당자가 나뉜 도메인 경계에서 상태값·식별자·정산 모수 규칙이 어긋나는 것을 막는다.
3. **화면·UI 파편화 방지 및 UIX팀(Figma) 직결**: HTML 프로토타입을 일일이 수작업으로 유지보수하지 않으면서도, 백오피스(AI 자체 프론트 구현)와 유저 프론트(UIX팀 Figma 협업) 각각의 화면 통일성을 100% 보장한다.
4. **PO(white)의 수동 검수 병목 제거**: 각자 로컬에서 **전용 스킬(`/doc-update`, `/dev-screen`, `/spec-check`)**을 거치고 GitHub에서 자동 테스트를 통과한 코드만 병합되게 하여, 사람이 일일이 코드를 대조하는 수고를 없앤다.

### 1.2 저장소 및 실행 구조 (산준모 기준 + 신규/레거시 범용)
- **정본 저장소 (`lcampus/sanjunmo-settlement`, 로컬 `D:\Work\Settlement`)**:
  - 기획 정본(`docs/`), 프로토타입(`prototype_clean/` — 산준모 기존 보유분), 정산 기준 계산기(`engine/php/` + 61건 시나리오), 위치 색인(`canon_index.md`), 화면 요약본(`digest/*.md`), 공통 도메인/UI 계약서(`00_domain_contracts.md`, `00_ui_system.md`) 보유.
- **개발 저장소 (`lcampus/sanjunmo`, 로컬 `D:\Work\sanjunmo`)**:
  - PHP 8.4 + Laravel 13.8 + MySQL 8.4 실제 애플리케이션 코드.
  - `.gitignore`에 등록된 `/docs` 폴더 아래로 정본 저장소의 색인·요약본·계약서·정본을 로컬 동기화(`scripts/sync-spec.sh`)해 참조.
- **검수 실행 위치 원칙 ("각자 로컬 스킬 실행 + 중앙 CI 코드 테스트")**:
  - 유료 외부 API 서버를 복잡하게 따로 구축하지 않고, **PO와 개발자가 각자 로컬 Claude Code에서 5대 스킬을 실행**해 정합성을 맞춘다.
  - GitHub 서버(CI)는 **결정론적 코드 검사(`check.sh`: Pint + 임시 MySQL 4병렬 테스트 + 정산 61건 계산기 일치 테스트)**만 수행한다.

## 2. 5대 핵심 스킬(Skill) 체계 및 직관적 명칭

복잡한 영문 전문용어 대신, 누가 봐도 역할을 바로 알 수 있는 **5개 스킬 이름**으로 통일한다.
- **`/doc-*` 계열 (문서·정본 관련 3종)**: `/doc-init`(01. 초기 정본 만들기), `/doc-rule`(02. 공통 규칙 뽑기), `/doc-update`(03. PO 정책 변경)
- **`/dev-*` 계열 (개발자 코딩 1종)**: `/dev-screen`(04. 개발자 화면 구현)
- **`/spec-*` 계열 (검수·대조 1종)**: `/spec-check`(05. 정본 대조 검수)

| 번호 | 스킬 명령어 | 한글 명칭 | 누가 · 언제 쓰는가 | 한 줄 요약 |
| :---: | :--- | :--- | :--- | :--- |
| **01** | **`/doc-init`** | **초기 정본 만들기** | • 정본 없는 레거시 서비스 온보딩 시 (최초 1회)<br>• 비정형 기획서를 표준 정본으로 변환할 때 | 코드/초안을 읽어 표준 3단 포맷(`[A]·[B]·[C]`) 정본 `v1.0.0` + 색인(`canon_index`) + 요약본(`digest`) 생성 |
| **02** | **`/doc-rule`** | **공통 규칙 뽑기** | • 초기 세팅 시 & 공통 코드·DB·UI 골격 변경 시 | 도메인 공통 계약(`00_domain_contracts.md`) 및 Track A 표준 화면 골격(`00_ui_system.md`) 추출·갱신 |
| **03** | **`/doc-update`** | **PO 정책 변경** | • **PO(white) 상시 사용**<br>• 특정 정책(환불·정산·할인 등)이나 화면 규칙을 고칠 때 | 영향 화면 스캔 보고 → 정본·계산기 개정 → `문서 개정 이력` 기록 → **개발팀 티켓 + UIX팀 Figma 수정 요청서** 동시 생성 |
| **04** | **`/dev-screen`** | **개발자 화면 구현** | • **개발자 4명 상시 사용**<br>• 담당 화면(`ADMN-*`, `USER-*`)을 개발·수정할 때 | Track A(표준 골격) 또는 **Track B(Figma MCP 직결)** 판별 + 정본 6% 핀셋 로드 → 계층 코딩 → `check.sh` 실행 |
| **05** | **`/spec-check`** | **정본 대조 검수** | • **개발자**(커밋 직전 셀프 검수)<br>• **PO(white)**(수시/병합 후 총괄 검수) | 정본 명세(+ Track B는 Figma MCP 노드)와 현재 코드를 대조해 **`✅ 일치` / `❌ 위반·누락` / `⚠️ 임의 구현`** 3가지로 판정 |

### 3.1 `/doc-init` — 초기 정본 만들기 스킬 (레거시 역공학 · 초안 포매팅)

```markdown
---
name: doc-init
description: 정본이 없는 레거시 프로젝트 코드나 비정형 기획 초안을 분석하여 표준 정본 문서(v1.0.0), 화면 요약본(digest), 위치 색인(canon_index)을 최초 생성한다.
---

# /doc-init (초기 정본 만들기) 실행 절차

## 1. 목적
정본(SSOT)이 없는 기존 유지보수 서비스나 비정형 기획서를 우리 에이전틱 파이프라인이 읽을 수 있는 **표준 정본 포맷**으로 구조화·포매팅한다. 코드는 수정하지 않는다.

## 2. 단계별 실행 규칙
1. **화면·기능 인벤토리 스캔 및 코드 채번**:
   - 대상 프로젝트의 `routes/`, `app/Http/Controllers/`, `resources/views/`, `database/migrations/`를 스캔한다.
   - 각 화면·모달·하위 페이지에 표준 화면 코드(`ADMN-<도메인>-<NNN>`, `USER-<도메인>-<NNN>`, 하위 페이지 `-S1`, 모달 `-P1`)를 부여하고 인벤토리 표를 만든다.
2. **표준 3단 템플릿 포매팅 (`docs/specs/`)**:
   - 반드시 아래 구조로 마크다운 문서를 작성한다:
     - 상단 헤더: `## 문서 개정 이력 (Revision History)` 표 (`v1.0.0 | YYYY-MM-DD | 초기 정본 구축`)
     - `[A] 프론트엔드(USER-*) ↔ 백오피스(ADMN-*) 1:1 페어 매핑표`
     - `[B] 화면별 상세 데이터 필드 및 입출력/모달 제어 명세`
     - `[C] 핵심 비즈니스 정책 및 하드락 가드레일`
3. **정상 정책 vs 레거시 의심 로직 분리 (중요)**:
   - 코드에 있는 분기문·계산식 중 정상 업무 규칙은 본문에 적고, 하드코딩·죽은 코드·모순으로 의심되는 부분은 정본으로 확정하지 말고 `docs/legacy_questions.md`에 `[PO 판정 요청 Q-01 ~ Q-NN]`으로 분리해 기록한다.
4. **색인 및 요약본 생성**:
   - 화면 코드별 문서·줄 번호 색인(`canon_index.md`)과 화면별 필드·상태 요약본(`digest/<화면코드>.md`)을 함께 생성한다.
```

### 3.2 `/doc-rule` — 공통 규칙 뽑기 스킬 (도메인 계약서 & UI 골격 계약서 생성·갱신)

```markdown
---
name: doc-rule
description: 정본 문서와 기준정보(common-master.js, config, DB 마이그레이션, 공통 레이아웃)에서 여러 개발자의 도메인이 공유하는 불변 비즈니스 규칙(00_domain_contracts.md)과 표준 UI 골격 규칙(00_ui_system.md)을 추출·갱신한다.
---

# /doc-rule (공통 규칙 뽑기) 실행 절차

## 1. 목적
수천 줄의 정본 문서 속에 흩어진 규칙 중, **도메인 간 경계에서 절대 어긋나면 안 되는 공통 비즈니스 계약(`00_domain_contracts.md`)**과 **프로토타입 없는 환경에서도 화면 통일성을 보장하는 UI 골격 계약(`00_ui_system.md`)**을 각각 1장짜리 문서로 압축해 모든 개발자의 AI가 작업 전 필독하게 한다.

## 2. `docs/contracts/00_domain_contracts.md` 필수 포함 6대 항목
1. **식별자 및 코드 채번 체계**:
   - 권리자 `RH-NNNN`(구 `INS-*`·`PY-*` 사용 금지), 거래처 `SUP-NNNN`, 계약 `CT-YYYY-NNNN`(`CON-*` 금지), 지원금 약정 `SFA-YYYY-NNN`, 도서 정식 SKU `PROD-BK-NNNN`(1xxx 자사, 2xxx 사입, 3xxx 위탁, 4xxx 비매품), 가채번 `BK-REQ-YYYY-NNNN`.
2. **계정 소속 및 권한 경계**:
   - 계정 소속 3종 고정(내부 직원 / 권리자 / 거래처). 역할 그룹은 운영자 권한 관리(`ADMN-CONF-005`)에서 관리하는 변수.
3. **공통 상태값 사전**:
   - 상품 판매 상태(판매대기·판매중·판매중지·판매종료 + 교재 예약판매·일시품절, 일반상품 품절), 1:1 문의 상태(접수·처리중·타부서 이관중·답변완료·보류), 정산·환불 상태값.
4. **화면 코드 통합·폐지 기준**:
   - 합격환급 심사 = `ADMN-SETT-006` 일원화(`ADMN-RFD-001` 뷰 폐지), 시스템 감사 로그 = `ADMN-CONF-010` 통합(`ADMN-CONF-006`은 3번 탭), 민감정보 보관·열람 통제 = `ADMN-USER-007`.
5. **1차 오픈 외부 연동 경계**:
   - 세금계산서(권리자 직접 발행·제출 + 홈택스 엑셀 대사, 역발행 미사용), 지급 이체(대량이체 엑셀 + 결과 대사, 펌뱅킹 2차), 메시지(네이버 클라우드 SENS), 본인인증(KG이니시스), 결제(토스페이먼츠).
6. **도메인 간 데이터 조작 금지 규칙**:
   - 타 담당자의 도메인 테이블을 직접 `insert/update/delete` 하지 않고 지정된 Service/Event 인터페이스를 거친다.

## 3. `docs/contracts/00_ui_system.md` 필수 포함 항목 (Track A / Track B 구분)
1. **Track A (AI 프론트 자체 구현 — 백오피스/어드민)**:
   - HTML 프로토타입을 개별 관리하지 않을 때 사용하는 **4대 표준 레이아웃 골격(`List-Modal`, `Detail-Form`, `Stats-Dashboard`, `Tabs-Complex`)**의 블레이드 컴포넌트 경로와 슬롯 규격 정의.
   - 검색 필터 배치(최대 3열), 금액 우측 정렬, 상태 배지 컬러 매핑(`대기=amber`, `진행=blue`, `완료=emerald`, `반려/오류=rose`), 상세 모달 호출 규칙 고정.
2. **Track B (UIX 팀 협업 — 유저 프론트/브랜드 화면)**:
   - 시각적 정본은 **UIX 팀의 Figma 시안(Figma MCP 연동)** 또는 UIX 퍼블리싱 마크업임을 명시.
   - Figma 프레임 명명 규칙(`[<화면코드>] 화면명`, 예: `[USER-MY-011] 환불내역`) 및 `Ready for Dev` 상태 게이트 정의.
```

```markdown
   - `docs/contracts/00_domain_contracts.md` (도메인 공통 계약) 및 `docs/contracts/00_ui_system.md` (UI 트랙 규칙)

## Step 2. 화면 트랙(Track A vs Track B) 판별 및 UI 소스 결합
1. **Track A (AI 프론트 자체 구현 — 주로 `ADMN-*` 백오피스)**:
   - 기존 HTML 프로토타입(`prototype_clean/`)이 있는 화면은 `digest` 요약본을 따르고, 프로토타입이 없는 신규/레거시 화면은 `00_ui_system.md`에 정의된 **4대 표준 화면 골격(`List-Modal`, `Detail-Form`, `Stats-Dashboard`, `Tabs-Complex`)** 블레이드 컴포넌트를 그대로 사용하여 정본 `[B]`의 검색필터·표 컬럼·모달을 배치한다(개발자 임의 레이아웃 창작 금지).
2. **Track B (UIX 팀 협업 — 주로 `USER-*` 유저 프론트)**:
   - 정본 `[B]`에 기록된 **Figma Node URL**(또는 Figma 파일 내 `[<화면코드>]` 프레임)을 확인하고 **Figma MCP 서버**를 호출하여 실제 레이아웃 구조(Auto Layout), 디자인 토큰, 텍스트 라벨, 컴포넌트 속성을 직접 읽어온다(또는 UIX 팀이 납품한 퍼블리싱 블레이드를 로드한다).
   - 만약 Figma 프레임이 아직 `Ready for Dev`(디자인 확정) 상태가 아니거나 정본의 필수 입력 필드가 Figma 시안에 누락되어 있다면, 임의로 UI를 그려 넣지 말고 즉시 보고한다.
   - **절대 금지**: Track B에서 로컬 AI가 UIX 팀의 DOM 구조나 스타일 클래스를 임의로 깨뜨리거나 바꾸지 않는다. AI는 오직 Figma/마크업 구조 위에 **변수 바인딩(`{{ $item }}`), 폼 액션, 유효성 검증, 비즈니스 로직**만 연결한다.

## Step 3. 미확정 정책 사전 차단 및 라라벨 계층 규격 구현
1. 정본이나 `DECISIONS`에 정의되지 않은 비즈니스 규칙·예외 처리가 발견되면 **임의로 추론해 코딩하지 않고 즉시 멈춘 뒤 PO 질문 항목으로 출력**한다(테스트는 `markTestIncomplete('DECISIONS 대기')`로 표기).
2. `Controller` → `Service` → `Repository` → `Model` 계층 규칙을 준수하여 코드를 작성하며, 타 도메인 테이블을 직접 조작하지 않는다.
3. 내가 수정하거나 새로 만든 `.php` 파일만 `./vendor/bin/pint <파일>`로 스타일을 맞춘다.
4. 정본의 핵심 검증 조건과 상태 전이를 검증하는 Feature/Unit 테스트를 함께 작성한다.

## Step 4. 셀프 대조(`/spec-check`) 및 프리체크(`check.sh`)

   - 예: `feat(settlement): 정산 수동 조정 라인 등록 검증 보강 (ADMN-SETT-005 · DECISIONS 208)`
```
