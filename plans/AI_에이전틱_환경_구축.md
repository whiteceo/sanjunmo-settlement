# [AI 에이전트 전용 명세서] AI 에이전틱 개발 · 정합성 검증 환경 구축 (v1.0)

> **문서 용도**: 이 문서는 **AI 에이전트(Claude Code · 안티그래비티)**가 프로젝트 환경을 세팅하거나, 각자의 역할(PO 정본 개정 / 개발자 화면 구현 / 정본↔코드 대조 검수 / 레거시 역공학 문서화)을 수행할 때 직접 읽고 따르는 **AI 실행 명세서(Executable Spec)**다.
> 사람(PO · 개발팀)에게 설명하고 브리핑하기 위한 시각 자료는 동일 폴더의 **`AI_에이전틱_환경_가이드.html`**을 사용한다.

---

## 1. 아키텍처 개요 및 핵심 원칙

### 1.1 왜 이 체계가 필요한가?
1. **작업자별 로컬 AI의 정본 이탈(Drift) 차단**: 여러 개발자가 각자 로컬에서 Claude Code로 코딩할 때, 정본을 안 읽거나 AI가 빈틈을 임의로 추론해 정본과 다른 로직·상태값·코드를 만드는 현상을 막는다.
2. **도메인 간 비즈니스 로직 충돌 방지**: 회원·권리자·정산 ↔ 주문·환불·쿠폰 ↔ 게시판·권한·로그처럼 담당자가 나뉜 도메인 경계에서 상태값·식별자·정산 모수 규칙이 어긋나는 것을 막는다.
3. **PO(white)의 수동 검수 병목 제거**: 각자 로컬에서 **전용 스킬(`/doc-update`, `/dev-screen`, `/spec-check`)**을 거치고 GitHub에서 자동 테스트를 통과한 코드만 병합되게 하여, 사람이 일일이 코드를 대조하는 수고를 없앤다.

### 1.2 저장소 및 실행 구조 (산준모 기준 + 신규/레거시 범용)
- **정본 저장소 (`lcampus/sanjunmo-settlement`, 로컬 `D:\Work\Settlement`)**:
  - 기획 정본(`docs/`), 프로토타입(`prototype_clean/`), 정산 기준 계산기(`engine/php/` + 61건 시나리오), 위치 색인(`canon_index.md`), 화면 요약본(`digest/*.md`), 공통 도메인 규칙(`00_domain_contracts.md`) 보유.
- **개발 저장소 (`lcampus/sanjunmo`, 로컬 `D:\Work\sanjunmo`)**:
  - PHP 8.4 + Laravel 13.8 + MySQL 8.4 실제 애플리케이션 코드.
  - `.gitignore`에 등록된 `/docs` 폴더 아래로 정본 저장소의 색인·요약본·계약서·정본을 로컬 동기화(`scripts/sync-spec.sh`)해 참조.
- **검수 실행 위치 원칙 ("각자 로컬 스킬 실행 + 중앙 CI 코드 테스트")**:
  - 유료 외부 API 서버를 복잡하게 따로 구축하지 않고, **PO와 개발자가 각자 로컬 Claude Code에서 5대 스킬을 실행**해 정합성을 맞춘다.
  - GitHub 서버(CI)는 **결정론적 코드 검사(`check.sh`: Pint + 임시 MySQL 4병렬 테스트 + 정산 61건 계산기 일치 테스트)**만 수행한다.

## 2. 5대 핵심 스킬(Skill) 체계 및 직관적 명칭

복잡한 영문 전문용어 대신, 누가 봐도 역할을 바로 알 수 있는 **5개 스킬 이름**으로 통일한다.
- **`/doc-*` 계열 (문서·정본 관련 3종)**: `/doc-init`(초기 정본 만들기), `/doc-rule`(공통 규칙 뽑기), `/doc-update`(PO 정책 변경)

### 3.1 `/doc-init` — 초기 정본 만들기 스킬 (레거시 역공학 · 초안 포매팅)

```markdown
---
name: doc-init
description: 정본이 없는 레거시 프로젝트 코드나 비정형 기획 초안을 분석하여 표준 정본 문서(v1.0.0), 화면 요약본(digest), 위치 색인(canon_index)을 최초 생성한다.
---

# /doc-init (초기 정본 만들기) 실행 절차

## 1. 목적
정본(SSOT)이 없는 기존 유지보수 서비스나 비정형 기획서를 우리 에이전틱 파이프라인이 읽을 수 있는 **표준 정본 포맷**으로 구조화·포매팅한다. 코드는 수정하지 않는다.

## 2. 단계별 실행 규칙
1. **화면·기능 인벤토리 스캔 및 코드 채번**:
   - 대상 프로젝트의 `routes/`, `app/Http/Controllers/`, `resources/views/`, `database/migrations/`를 스캔한다.
   - 각 화면·모달·하위 페이지에 표준 화면 코드(`ADMN-<도메인>-<NNN>`, `USER-<도메인>-<NNN>`, 하위 페이지 `-S1`, 모달 `-P1`)를 부여하고 인벤토리 표를 만든다.
2. **표준 3단 템플릿 포매팅 (`docs/specs/`)**:
   - 반드시 아래 구조로 마크다운 문서를 작성한다:
     - 상단 헤더: `## 문서 개정 이력 (Revision History)` 표 (`v1.0.0 | YYYY-MM-DD | 초기 정본 구축`)
     - `[A] 프론트엔드(USER-*) ↔ 백오피스(ADMN-*) 1:1 페어 매핑표`
     - `[B] 화면별 상세 데이터 필드 및 입출력/모달 제어 명세`
     - `[C] 핵심 비즈니스 정책 및 하드락 가드레일`
3. **정상 정책 vs 레거시 의심 로직 분리 (중요)**:
   - 코드에 있는 분기문·계산식 중 정상 업무 규칙은 본문에 적고, 하드코딩·죽은 코드·모순으로 의심되는 부분은 정본으로 확정하지 말고 `docs/legacy_questions.md`에 `[PO 판정 요청 Q-01 ~ Q-NN]`으로 분리해 기록한다.
4. **색인 및 요약본 생성**:
   - 화면 코드별 문서·줄 번호 색인(`canon_index.md`)과 화면별 필드·상태 요약본(`digest/<화면코드>.md`)을 함께 생성한다.
```

```markdown
# /doc-rule (공통 규칙 뽑기) 실행 절차

## 1. 목적
수천 줄의 정본 문서 속에 흩어진 규칙 중, **도메인 간 경계에서 절대 어긋나면 안 되는 공통 계약**만 1장짜리 문서(`00_domain_contracts.md`)로 압축해 모든 개발자의 AI가 작업 전 필독하게 한다.

## 2. 반드시 포함할 6대 계약 항목
1. **식별자 및 코드 채번 체계**:
   - 권리자 `RH-NNNN`(구 `INS-*`·`PY-*` 사용 금지), 거래처 `SUP-NNNN`, 계약 `CT-YYYY-NNNN`(`CON-*` 금지), 지원금 약정 `SFA-YYYY-NNN`, 도서 정식 SKU `PROD-BK-NNNN`(1xxx 자사, 2xxx 사입, 3xxx 위탁, 4xxx 비매품), 가채번 `BK-REQ-YYYY-NNNN`.
2. **계정 소속 및 권한 경계**:
   - 계정 소속 3종 고정(내부 직원 / 권리자 / 거래처). 역할 그룹은 운영자 권한 관리(`ADMN-CONF-005`)에서 관리하는 변수.
3. **공통 상태값 사전**:
   - 상품 판매 상태(판매대기·판매중·판매중지·판매종료 + 교재 예약판매·일시품절, 일반상품 품절), 1:1 문의 상태(접수·처리중·타부서 이관중·답변완료·보류), 정산·환불 상태값.
4. **화면 코드 통합·폐지 기준**:
   - 합격환급 심사 = `ADMN-SETT-006` 일원화(`ADMN-RFD-001` 뷰 폐지), 시스템 감사 로그 = `ADMN-CONF-010` 통합(`ADMN-CONF-006`은 3번 탭), 민감정보 보관·열람 통제 = `ADMN-USER-007`.
5. **1차 오픈 외부 연동 경계**:
   - 세금계산서(권리자 직접 발행·제출 + 홈택스 엑셀 대사, 역발행 미사용), 지급 이체(대량이체 엑셀 + 결과 대사, 펌뱅킹 2차), 메시지(네이버 클라우드 SENS), 본인인증(KG이니시스), 결제(토스페이먼츠).
6. **도메인 간 데이터 조작 금지 규칙**:
   - 타 담당자의 도메인 테이블을 직접 `insert/update/delete` 하지 않고 지정된 Service/Event 인터페이스를 거친다.
```

### 3.3 `/doc-update` — PO 정책 변경 스킬 (영향도 스캔 → 일괄 개정 → 개정이력 & 티켓)

```markdown
---
name: doc-update
description: PO(white)가 정책이나 화면 규칙 변경을 지시할 때, 영향받는 모든 문서 절과 화면 코드를 먼저 스캔해 보고하고, 승인 후 정본·프로토타입·계산기 일괄 개정 및 문서 개정이력 기록, 개발팀 전달용 변경 티켓 생성을 수행한다.
---

# /doc-update (PO 정책 변경) 실행 절차

## Step 1. 영향도 전수 스캔 및 브리핑 (파일 수정 전 필수)
1. PO가 변경할 정책(예: 환불 정책, 정산 산식, 상태 규칙 등)을 지시하면 곧바로 파일을 고치지 않는다.
2. `canon_index.md`, 정본 문서(`docs/산준모닷컴 구축 통합 상세 설계서.md`, `docs/[산준모 정산시스템]_00~04.md`), 프로토타입(`prototype_clean/`), 정산 계산기(`engine/php/`)를 검색하여 아래 표를 먼저 PO에게 보고한다:
   - **영향받는 정본 문서 및 절/줄 번호**
   - **영향받는 전체 화면 코드 목록 (`ADMN-*`, `USER-*`)**
   - **프로토타입 HTML 및 정산 계산기(`engine/`) 수정 필요 여부**

## Step 2. 정본 · 프로토타입 · 계산기 일괄 개정
1. PO가 영향 범위를 승인하면, 관련 정본 문서의 본문을 인라인으로 수정한다(하단에 새 장 덧붙이기 금지).
2. 프로토타입 수정이 필요하면 `prototype_clean/` 수정 후 `mirror_patch.py`로 `prototype/`에 동시 반영하고, 계산기 로직이 바뀌면 `engine/`(Python + PHP 8.4)과 시나리오 JSON을 함께 갱신한다.

## Step 3. 문서 개정이력(Revision History) 기록 및 색인 갱신
1. 수정된 정본 문서 상단의 `## 문서 개정 이력 (Revision History)` 표 맨 아래에 **새 버전 행(예: `v3.2.32` / `v4.0.9`)**을 추가한다.
2. 개정이력 요약 칸에는 반드시 **영향받은 화면 코드(`ADMN-*`, `USER-*`)**를 모두 명시한다.
3. `python scripts/qa/build_canon_index.py`와 `python scripts/qa/build_screen_digest.py`를 실행해 색인과 요약본을 최신화하고, QA 스크립트(`skill_static_lint.py`, `skill_cross_data_check.py`, `skill_pair_diff.py`, `E2E`)를 통과시킨다.

## Step 4. 커밋 · 동기화 및 개발팀(`sanjunmo`) 변경 알림 생성
1. PO에게 diff를 보여주고 승인 후 Git 커밋·푸시 및 동기화를 수행한다.
2. 방금 추가한 `문서 개정 이력` 행의 화면 코드들을 `D:\Work\sanjunmo\config\dev-progress.php`의 담당자 배분표와 대조하여, **담당 개발자(박성민·노승원·이응민)별로 어떤 화면의 어떤 규칙을 고쳐야 하는지 정리한 변경 통지문(또는 GitHub Issue)**을 출력한다.
```

### 3.4 `/dev-screen` — 개발자 화면 구현 스킬 (컨텍스트 절약 로더 & 표준 구현)

```markdown
---
name: dev-screen
description: 개발자가 특정 화면 코드(ADMN-*, USER-*)를 구현하거나 수정할 때, 정본 전체를 읽지 않고 해당 화면의 색인 구간·요약본(digest)·도메인 계약서만 로드하여 계층 규칙에 맞게 구현하고 check.sh로 검증한다.

# /dev-screen (개발자 화면 구현) 실행 절차

## Step 1. 정본 최신화 및 타겟 컨텍스트 핀셋 로드
1. 입력받은 화면 코드(예: `ADMN-SETT-005`, `USER-MY-011`)를 확인한다.
2. 로컬 `docs/` 폴더에 최신 정본이 동기화되어 있는지 확인한다(`bash scripts/sync-spec.sh`).
3. **절대 정본 마크다운 전체를 통째로 읽지 않는다.** 아래 3가지만 핀셋으로 읽는다:
   - `docs/contracts/00_domain_contracts.md` (도메인 공통 계약)
   - `docs/canon_index.md`에서 대상 화면 코드가 위치한 정본 문서의 **해당 줄 번호 구간(±50줄)**
   - `docs/digest/<화면코드>_baseline.md` (백오피스 화면인 경우 입력 필드·상태·모달 요약본)

## Step 2. 미확정 정책 사전 차단 및 구현 계획 브리핑
1. 읽어들인 정본 명세와 현재 `app/` 코드를 비교하여 구현 계획을 짧게 브리핑한다.
2. 만약 정본이나 `DECISIONS`에 정의되지 않은 비즈니스 규칙·예외 처리가 발견되면 **임의로 추론해 코딩하지 않고 즉시 멈춘 뒤 PO 질문 항목으로 출력**한다(테스트는 `markTestIncomplete('DECISIONS 대기')`로 표기).

## Step 3. 라라벨 계층 규격 구현 및 회귀 테스트 작성
1. `Controller` → `Service` → `Repository` → `Model` 계층 규칙을 준수하여 코드를 작성한다.
2. 다른 개발자 도메인의 테이블/모델을 직접 조작하지 않는다.
3. 내가 수정하거나 새로 만든 `.php` 파일만 `./vendor/bin/pint <파일>`로 스타일을 맞춘다(기존 파일 전체 재포맷 커밋 금지).
4. 정본의 핵심 검증 조건과 상태 전이를 검증하는 Feature/Unit 테스트를 함께 작성한다.

## Step 4. 셀프 대조(`/spec-check`) 및 프리체크(`check.sh`)
1. 구현한 코드가 정본 명세의 필드·상태·규칙을 빠짐없이 충족하는지 대조한다.
2. `bash scripts/check.sh`를 실행해 Pint와 임시 MySQL 병렬 테스트를 통과시킨다.
3. 커밋 메시지 제목/본문에 화면 코드와 의사결정 번호를 포함한 초안을 제시한다:
   - 예: `feat(settlement): 정산 수동 조정 라인 등록 검증 보강 (ADMN-SETT-005 · DECISIONS 208)`
```

```markdown
- **PO 총괄 감사 모드**: PO가 지정한 화면 코드 목록, 특정 도메인, 또는 최근 `dev` 병합 커밋들의 화면 코드를 대상으로 `D:\Work\Settlement`(정본)와 `D:\Work\sanjunmo`(개발 코드)를 직접 대조한다.

## 2. 대조 기준 로드
1. 대상 화면 코드(`ADMN-*`, `USER-*`)에 해당하는:
   - `00_domain_contracts.md` (코드 체계, 상태값, 소속 3분류, 외부 연동 경계)

   - `digest/<화면코드>_baseline.md` (필드, 옵션, 표 헤더, 버튼/모달, 상태값)

## 3. 판정 및 리포트 출력 규칙 (문서·코드 임의 수정 금지)

| 판정 | 의미 | 후속 조치 |
```

## 4. 사람들이 지켜야 할 규약 요약 (Part B)

시스템과 5대 스킬이 정상 작동하기 위해 PO와 개발자 4명이 지키는 약속이다.

1. **[공통] 모든 작업·브랜치·커밋에는 ‘화면 코드(`ADMN-*`, `USER-*`)’를 적는다**
   - 화면 코드가 열쇠(Key)다. 코드가 있어야 `/dev-screen`과 `/spec-check`가 어느 정본을 읽을지 찾고, `dev-progress`가 진행률을 자동 집계한다.
2. **[PO] 구두·카톡 지시 대신 `/doc-update`로 정본과 `문서 개정 이력`을 먼저 고친다**
   - PO는 파일을 직접 열지 않고 로컬 AI에게 `/doc-update`를 시켜 영향 화면을 스캔하고 `문서 개정 이력`에 남긴다. 구두로만 지시하면 개발자 코드가 `/spec-check`에서 *"정본 위반"*으로 막힌다.
3. **[개발자] 코딩 시작할 땐 `/dev-screen`, 커밋 직전엔 `/spec-check` + `check.sh`를 거친다**
   - 정본을 통째로 읽히지 말고 `/dev-screen <화면코드>`로 작업하고, 커밋 전에 `/spec-check`와 `bash scripts/check.sh`를 통과한 코드만 올린다.
4. **[개발자] 정본에 없는 정책은 임의로 짜지 않고 멈춘다**
   - 애매한 정책은 AI가 추론하게 두지 말고 `markTestIncomplete` 처리 후 PO에게 알려 `/doc-update`로 정본에 먼저 반영되게 한다.
5. **[개발자] 남의 도메인 테이블을 직접 수정하지 않는다**
   - `00_domain_contracts.md`에 정의된 공통 코드와 Service/Event 경계를 지킨다.
