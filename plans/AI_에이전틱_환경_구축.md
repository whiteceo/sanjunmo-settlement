# [AI 에이전트 전용 명세서] AI 에이전틱 개발 · 정합성 검증 환경 구축 (v1.2)

> **문서 용도**: 이 문서는 **AI 에이전트(Claude Code · 안티그래비티)**가 프로젝트 환경을 세팅하거나, 각자의 역할(**PO/PM** 정본 개정 / **UIX 디자이너** Figma 연동 / **개발자** 화면 구현 / 정본↔코드 대조 검수 / 레거시 역공학 문서화)을 수행할 때 직접 읽고 따르는 **AI 실행 명세서(Executable Spec)**다.
> 사람(**PO/PM · UIX 디자이너 · 개발자**)에게 설명하고 브리핑하기 위한 시각 자료는 동일 폴더의 **`AI_에이전틱_환경_가이드.html`**을 사용한다.

## 0. 핵심 용어 사전 (Glossary)

문서 전반에서 사용되는 약어와 핵심 개념의 정의다. 본문에서도 첫 등장 시 한글 풀이를 병기한다.

| 용어 (약어) | 한글 명칭 | 쉬운 풀이 및 실무 역할 |
| :--- | :--- | :--- |
| **SSOT** (`Single Source of Truth`) | **단일 정본 (유일 기준 원본)** | 기획서·정책서·화면 명세가 여러 곳에 흩어지지 않고, **오직 한 곳(`spec-repo/docs/`)의 문서만 절대 기준으로 삼는 원칙**. 정본에 없는 내용은 버그로 간주한다. |
| **PO / PM** (`Product Owner / Manager`) | **프로덕트 오너 / 매니저** | 비즈니스 정책·화면 기획·우선순위를 결정하고 정본(SSOT)의 최종 승인 권한을 갖는 기획 책임자 그룹(다수 도메인 PM + 리드 PO/PM 포함). |
| **MCP** (`Model Context Protocol`) | **모델 컨텍스트 프로토콜 (외부 도구 직결 통로)** | AI 에이전트가 로컬 파일뿐 아니라 **Figma 디자인 시안, 사내 업무 게시판, DB 스키마 등 외부 도구의 실시간 데이터를 직접 읽어오는 표준 연결 규격**. |
| **Digest** (`Screen Digest`) | **화면별 1장 요약본** | 수천 줄짜리 전체 정본 문서 중 **특정 화면 코드 1개에 필요한 데이터 필드·상태값·모달·핵심 수식만 1~2장으로 자동 추출한 AI용 요약 카드**. |
| **Archetype** (`UI Archetype`) | **표준 화면 골격 (4종)** | 프로토타입 HTML 없이도 백오피스 화면의 통일성을 유지하도록 미리 정해둔 **4가지 표준 레이아웃 틀** (`List-Modal`, `Detail-Form`, `Stats-Dashboard`, `Tabs-Complex`). |
| **Auto Layout & Design Token** | **자동 반응형 배치 & 디자인 변수** | UIX 디자이너가 Figma에서 여백·정렬·반응형 크기(Auto Layout)와 색상·폰트·간격 변수(Design Token)를 규격화해 두어 AI가 오차 없이 코드로 변환하게 하는 설정. |
| **Greenfield / Brownfield** | **신규 구축 / 레거시 유지보수** | **Greenfield**는 백지상태에서 새로 만드는 프로젝트, **Brownfield**는 기존에 돌아가는 레거시 코드 위에 기능을 고치거나 덧붙이는 프로젝트. |
| **Fast-Track** (`Level 1~3`) | **변경 등급별 경량 경로** | 모든 수정을 똑같은 무거운 절차로 돌리지 않고, **신규/대규모(L1) · 로직만 변경(L2, UIX 생략) · 단순문구/긴급장애(L3, 선조치 후동기화)**로 나누어 처리 속도를 높이는 규칙. |

## 1. 아키텍처 개요 및 핵심 원칙

### 1.1 왜 이 체계가 필요한가?
1. **다수 작업자 로컬 AI의 정본 이탈(Drift) 차단**: 여러 명의 개발자가 각자 로컬에서 AI로 코딩할 때, 정본(SSOT, 단일 정본)을 안 읽거나 AI가 빈틈을 임의로 추론해 정본과 다른 로직·상태값·코드를 만드는 현상을 원천 차단한다.
2. **다중 도메인 간 비즈니스 로직 충돌 방지**: 다수의 **PO/PM**과 다수의 **개발자(프론트엔드·백엔드)**가 도메인(회원·권리자·정산 ↔ 주문·환불·쿠폰 ↔ 권한·로그 등)을 나누어 병렬 작업할 때 상태값·식별자·계산식·API 스키마가 어긋나는 것을 막는다.
3. **화면·UI 파편화 방지 및 UIX(Figma) 직결**: 정적 HTML 프로토타입을 수작업으로 유지보수하지 않으면서도, 백오피스(Track A: AI 표준 골격 구현)와 유저 프론트(Track B: UIX 디자이너 Figma MCP 협업) 각각의 화면 통일성을 100% 보장한다.
4. **PO/PM의 수동 검수 병목 제거**: 각 파트 작업자가 로컬에서 **5대 스킬(`/doc-init`, `/doc-rule`, `/doc-update`, `/dev-screen`, `/spec-check`)**을 거치고 중앙 CI 자동 테스트를 통과한 코드만 병합되게 하여, 사람이 일일이 눈으로 대조하는 병목을 없앤다.

### 1.2 범용 저장소 구조 (모든 프로젝트 공통 규격)
- **정본 저장소 (`spec-repo`, 예: `sanjunmo-settlement`)**:
  - 기획 정본(`docs/`), 도메인 기준 계산기(`engine/` + 검증 시나리오 JSON), 위치 색인(`canon_index.md`), 화면 요약본(`digest/*.md`), 공통 도메인 계약(`00_domain_contracts.md` — API Mock JSON 포함), 표준 UI 계약(`00_ui_system.md`) 보유.
- **개발 저장소 (`app-repo`, 예: `sanjunmo`)**:
  - 실제 백엔드·프론트엔드 애플리케이션 코드.
  - `.gitignore`에 등록된 `/docs` 폴더 아래로 정본 저장소의 색인·요약본·계약서·정본을 로컬 동기화(`scripts/sync-spec.sh`)해 참조.
- **검수 실행 위치 원칙 ("각자 로컬 스킬 실행 + 중앙 CI 코드 테스트")**:
  - 별도 유료 외부 서버 구축 없이 **PO/PM, UIX 디자이너(핸드오프 검증), 개발자가 각자 로컬 환경에서 스킬을 실행**해 정합성을 맞춘다.
  - GitHub 서버(CI)는 **결정론적 코드 검사(`check.sh`: 코드 스타일 + 임시 DB 병렬 테스트 + 도메인 계산기 정답 대조)**만 수행한다.

### 1.3 프론트엔드·화면 설계 2-Track 이원화 전략 (프로토타입 관리 부담 제거 & UIX Figma 직결)
별도의 HTML 프로토타입 파일을 수십 개씩 만들고 유지보수하는 부담을 없애기 위해, 화면의 성격에 따라 **Track A**와 **Track B**로 명확히 구분해 운영한다.

| 구분 | **Track A: AI 프론트 자체 구현 트랙** (백오피스 · 어드민 · 사내 툴) | **Track B: UIX 디자이너 협업 트랙** (유저 프론트 · 브랜드 웹/앱) |
| :--- | :--- | :--- |
| **시각적 기준 (SSOT)** | **`00_ui_system.md` (표준 화면 골격 4종 아키타입)** + 정본 `[B] 화면 명세` 표 | **UIX 디자이너의 Figma 시안 (Figma MCP 서버 직결)** + 정본 `[B] 데이터/상태 명세` |
| **HTML 프로토타입 관리** | **생략** (필요시 PO/PM이 4종 골격 기반 1회성 임시 프리뷰만 띄워 보고 폐기) | **생략** (Figma 프레임 자체가 시각 정본 역할 수행) |
| **연결 열쇠 (Key)** | 화면 코드(`ADMN-*`) + 골격 유형(`List-Modal`, `Detail-Form`, `Stats-Dashboard`, `Tabs-Complex`) | Figma 프레임명에 **`[USER-MY-011]`** 화면 코드 표기 + 정본에 Figma Node URL 기록 |
| **`/dev-screen` 작동 방식** | 지정된 표준 UI 컴포넌트 골격에 검색필터·컬럼·모달·비즈니스 로직을 일괄 생성 | **Figma MCP**로 실제 DOM/Auto Layout(자동 반응형 배치)/Design Token(디자인 변수)을 읽어 마크업 생성 + 정본의 비즈니스 로직·데이터 바인딩만 결합 (**AI 임의 UI 변형 금지**) |
| **`/spec-check` 검수 기준** | 정본 `[B]`의 필터·컬럼·모달 구성 및 `[C]` 비즈니스 로직 일치 여부 | **Figma(MCP) 시안의 입력폼·버튼·배지 누락 여부** + **정본 `[C]` 비즈니스 로직 일치 여부** 동시 대조 |

### 1.4 다중 작업자(Multi-PM · Multi-UIX · Multi-Dev) 협업 및 지시·피드백 전달 아키텍처

PO/PM, UIX 디자이너, 개발자가 각각 **여러 명(N:M:K)**인 조직에서 **사람이 화면코드를 일일이 외우거나 복사·붙여넣기(복붙) 하지 않고** 설계·변경·역질문을 주고받기 위한 구조다. **외부 툴 없이 Git 자체만으로 100% 완결되는 기본(Core) 구조** 위에, 조직 환경에 따라 **사내 업무플랫폼 API 등을 붙이는 확장 제안(Optional Add-on)**으로 구분한다.

#### (1) 소통 단위 원칙: ‘사람은 안건(주제) 단위로 말하고, 화면코드 매핑은 AI가 자동 수행’
- 실제 기획 추가나 정책 수정은 화면 1개 단위가 아니라 *"부분환불 수수료 규정 변경"*, *"신규 쿠폰 도입"*처럼 **여러 화면에 동시에 걸치거나 화면이 없는 백엔드 정책(안건/Topic 단위)**으로 발생한다.
- 따라서 사람은 화면코드를 일일이 찾아 적지 않고 **자연어 ‘안건(주제)’ 단위로만 소통**하며, `/doc-update`를 실행한 AI가 정본 전체를 스캔해 **영향받는 화면코드들(`USER-*`, `ADMN-*`)과 도메인 모듈을 자동으로 추출·태깅**한다.

#### (2) 다중 인원 동시 작업 시 충돌 방지 규칙
1. **다수의 PO/PM (도메인별 PM 분담 시)**:
   - 정본 마크다운 파일을 도메인별로 분리(`01_회원_권한.md`, `02_상품_주문.md`, `03_정산_환불.md`)하여 담당 PM 오너십을 지정한다.
   - 여러 도메인에 걸치는 **`00_domain_contracts.md`(공통 계약·상태값·API Mock) 수정 시에는 반드시 리드 PO/PM의 승인**을 거친다.
2. **다수의 UIX 디자이너**:
   - Figma 프레임 이름에 **`[<화면코드>] 화면명` (예: `[USER-MY-011] 환불신청모달`)**을 부여하고, 디자인 작업 중(`WIP`)과 확정(`Ready for Dev`) 상태를 구분한다.
   - `Ready for Dev`가 찍히지 않은 프레임은 개발자 AI(`/dev-screen`)가 코드 생성을 거부하여 미완성 시안 구현을 방지한다.
3. **다수의 개발자 (FE/BE 병렬 개발)**:
   - 백엔드 API 개발이 끝나기 전에 프론트엔드 개발자가 먼저 화면을 구현할 수 있도록, `/doc-rule`이 `00_domain_contracts.md`에 **표준 API 요청/응답 Mock JSON 스키마**를 함께 정의한다.

#### (3) 변경 규모별 3단계 패스트트랙 (Fast-Track) 전달 경로
모든 변경을 단일 경로로 처리하면 병목이 생기므로, `/doc-update` 실행 시 변경 등급(`Level 1~3`)을 자동 판별하여 전달 경로를 분기한다.

| 변경 등급 | 해당 케이스 | 전달 및 실행 경로 (라우팅) |
| :---: | :--- | :--- |
| **Level 1 (Full Track)** | • 신규 화면 추가<br>• 정책 변경으로 **화면 UI 요소(입력창·버튼·배지)와 비즈니스 로직이 함께 바뀔 때** | `PO/PM (/doc-update)` ➔ **`UIX 지시서 + 개발 지시서 동시 생성`** ➔ `UIX Figma 반영(Ready for Dev)` ➔ `개발자 (/dev-screen)` ➔ `양방향 검수 (/spec-check)` |
| **Level 2 (Logic Fast-Track)** | • 화면 레이아웃·UI 변경 없이 **정산 수식·할인율·유효성 조건·DB 로직만 바뀔 때** | `PO/PM (/doc-update)` ➔ **`UIX 단계 생략 (개발 지시서만 생성)`** ➔ `개발자 (/dev-screen)` ➔ `정본 검수 (/spec-check)` |
| **Level 3 (Micro / Hotfix)** | • 단순 문구·오탈자 수정<br>• 운영 긴급 장애(Hotfix) 선조치 | 선(先) 수정 조치 후 **`/doc-update --sync-from-code`**로 정본 및 개정이력 사후 동기화 |

#### (4) 지시·피드백 전달 채널: [기본(Core) Git 내장 지시서 MD] vs [확장 제안(Option) 사내 업무플랫폼 API 직결]
별도의 외부 툴이나 사내 플랫폼 개편 없이도 **Git 저장소 하나만으로 복붙 0%로 돌아가는 기본 방식**과, 사내 업무플랫폼을 연동하는 **확장 제안 방식**이다.

| 구분 | **[기본 (Core)] Git 내장 지시서 & 피드백 MD (외부 의존성 0)** | **[확장 제안 (Option A)] 사내 업무플랫폼 경량 API 직결** | **[대안 (Option B)] Google Workspace 연동** |
| :--- | :--- | :--- | :--- |
| **작동 원리** | • PO/PM이 `/doc-update` 실행 시 정본 개정과 함께 **`docs/changes/LATEST_TASK.md` (변경 안건·영향 화면코드·파트별 지시사항)** 파일이 Git에 자동 생성·푸시됨<br>• PO/PM은 *"정본 올렸으니 확인해"* 한마디만 전달<br>• 개발자의 로컬 AI가 `sync-spec.sh` 후 **`LATEST_TASK.md`를 직접 읽어** 이번 지시사항을 즉시 파악하고 구현 착수 | • 사내 업무플랫폼(자체 구축 게시판)에 **AI 전용 경량 REST API 3종(`POST 안건등록`, `GET 피드백조회`, `PATCH 상태변경`)** 개방<br>• 초기 1회 동기화한 **`project-meta.json` (프로젝트 ID + 부서·도메인별 담당자 명단)**을 읽고 AI가 프로젝트 선택 및 담당자 지정을 자동 세팅해 게시 | • 사내 플랫폼 API 개방 전 과도기 또는 외부 협업 시, AI에 기본 내장된 **GWS MCP/CLI**로 Google Sheets(안건 상태판) 및 Google Chat 스페이스에 자동 등록·조회 |
| **역질문(❓) 수렴** | • 개발 중 미정의 케이스 발견 시 `/dev-screen`이 `docs/changes/QUESTIONS.md`(또는 PR 코멘트)에 역질문을 자동 기록 ➔ PO/PM의 AI가 읽고 정본 보완 | • 개발자·UIX가 사내 업무플랫폼 안건 게시글에 댓글(또는 AI 자동 댓글)을 달면, PO/PM의 AI가 `GET` API로 댓글을 직접 읽어와 브리핑 | • Google Sheets 행 코멘트 또는 Chat 스레드를 AI가 직접 읽어와 브리핑 |
| **장점** | **추가 개발 공수 0건**, 즉시 가동 가능, 코드·정본·지시서가 Git 히스토리에 완벽히 일치 | 전 직원이 익숙한 사내 공식 플랫폼으로 일원화, 비개발자(UIX·타부서) 웹 접근성 최상 | 별도 API 개발 없이 즉시 외부 협업 가능 |

### 1.5 파이프라인 전(Before) vs 후(After): 파트별 사람(Human)이 직접 하는 일

AI 파이프라인이 돌아가기 **전(투입·설계)**과 돌아간 **후(검토·승인)**에 각 직책의 **사람이 직접 수행하는 핵심 역할**이다.

| 직책 (다수 인원) | **[파이프라인 전 (Before)] 사람이 직접 하는 일** | **[AI 파이프라인 자동 처리 구간]** | **[파이프라인 후 (After)] 사람이 직접 하는 일** |
| :--- | :--- | :--- | :--- |
| **PO / PM**<br>(기획·정책 그룹) | • 비즈니스 안건(요구사항) 결정<br>• 로컬 AI에 `/doc-update`로 자연어 안건 지시 (화면코드 암기 불필요) | • 변경 등급(L1~L3) 판별 및 영향받는 정본 절·화면코드 전수 스캔<br>• 정본 MD·계산기·색인·Digest·API Mock 일괄 갱신<br>• **`docs/changes/LATEST_TASK.md` 지시서 생성** (+ 확장 시 사내 플랫폼 API로 담당자 자동 매핑 게시) | • AI가 스캔한 영향 범위 및 정본 diff 최종 승인 후 Git 푸시 (*"정본 반영됨"* 공유)<br>• UIX·개발 파트에서 올라온 **역질문(`❓ 미정의 케이스`) 의사결정 판정** |
| **UIX 디자이너**<br>(디자인 그룹) | • 변경 지시서(`LATEST_TASK.md` 또는 사내 플랫폼 알림)의 UIX 요청 사항 확인 (`L2 로직변경` 시 생략)<br>• Figma에서 `[화면코드]` 프레임 디자인 및 Auto Layout·Design Token 적용 | • **Figma MCP 서버**가 확정된(`Ready for Dev`) 프레임의 구조·스타일·토큰을 개발자 AI에게 실시간 공급 | • 완료된 프레임을 **`Ready for Dev`** 상태로 전환하고 Figma 노드 URL 공유<br>• 디자인 중 발견된 레이아웃 한계는 역피드백 등록, 배포 후 `/spec-check` 시각 리포트 확인 |
| **개발자**<br>(FE / BE 그룹) | • `sync-spec.sh` 실행 후 로컬 AI에 *"이번 변경 지시사항 확인해서 구현해"* (`/dev-screen`) 지시 | • **`LATEST_TASK.md`에서 내 담당 화면코드 자동 인식**<br>• 정본 6% 명세 + Track A(표준 골격) / Track B(Figma MCP) 결합 코딩<br>• 단위/기능 테스트 작성, `check.sh` 및 `/spec-check` 자동 대조 | • 코딩 중 발견된 **`❓ 정본 미정의 항목`은 임의 추론 없이 역질문으로 등록**<br>• `/spec-check`의 `❌ 위반/누락 0건` 확인 후 PR 생성 및 동료 코드 리뷰 |

### 3.1 `/doc-init` — 초기 정본 만들기 스킬 (신규 초안 포매팅 · 레거시 역공학)

```markdown
---
name: doc-init
description: 정본(SSOT)이 없는 레거시 프로젝트 코드나 신규 프로젝트의 비정형 기획 초안을 분석하여 표준 정본 문서(v1.0.0), 화면 요약본(digest), 위치 색인(canon_index)을 최초 생성한다.
---

# /doc-init (초기 정본 만들기) 실행 절차

## 1. 목적
정본(SSOT, 단일 정본)이 없는 기존 유지보수 서비스(Brownfield)나 신규 구축(Greenfield) 초안을 에이전틱 파이프라인이 읽을 수 있는 **표준 정본 포맷**으로 구조화한다. 코드는 수정하지 않는다.

## 2. 단계별 실행 규칙
1. **화면·기능 인벤토리 스캔 및 코드 채번**:
   - 대상 프로젝트의 라우트, 컨트롤러, 뷰, DB 마이그레이션을 스캔(또는 기획 초안 분석)한다.
   - 각 화면·모달·하위 페이지에 표준 화면 코드(`ADMN-<도메인>-<NNN>`, `USER-<도메인>-<NNN>`, 하위 페이지 `-S1`, 모달 `-P1`)와 UI 트랙(Track A 백오피스 / Track B UIX Figma)을 부여한다.
2. **표준 3단 템플릿 포매팅 (`docs/specs/`)**:
   - 상단 헤더: `## 문서 개정 이력 (Revision History)` 표 (`v1.0.0 | YYYY-MM-DD | 담당 PO/PM | 초기 정본 구축`)
   - `[A] 프론트엔드(USER-*) ↔ 백오피스(ADMN-*) 1:1 페어 매핑표`
   - `[B] 화면별 상세 데이터 필드, UI 트랙(Track A 골격명 / Track B Figma URL), 입출력/모달 제어 명세`
   - `[C] 핵심 비즈니스 정책 및 하드락 가드레일`
3. **정상 정책 vs 레거시 의심 로직 분리 (Brownfield 중요 규칙)**:
   - 하드코딩·죽은 코드·모순으로 의심되는 부분은 정본으로 확정하지 말고 `docs/legacy_questions.md`에 `[PO/PM 판정 요청 Q-01 ~ Q-NN]`으로 분리해 사내 업무플랫폼 등록용 포맷으로 출력한다.
4. **색인 및 요약본 생성**:
   - 화면 코드별 문서·줄 번호 색인(`canon_index.md`)과 화면별 요약본(`digest/<화면코드>.md`)을 함께 생성한다.
```

```markdown
# /doc-rule (공통 규칙 뽑기) 실행 절차

## 1. 목적
도메인 간 경계에서 절대 어긋나면 안 되는 **공통 비즈니스 및 API Mock 계약(`00_domain_contracts.md`)**과 **2-Track 화면 통일성 계약(`00_ui_system.md`)**을 각각 압축해 모든 작업자의 AI가 작업 전 필독하게 한다.

## 2. `docs/contracts/00_domain_contracts.md` 필수 포함 항목
1. **식별자 및 코드 채번 체계**: 도메인별 고유 식별자 프리픽스 및 구 코드 사용 금지 규칙.
2. **계정 소속 및 권한 경계**: 계정 유형 및 역할 그룹 권한 제어 기준.
3. **공통 상태값 사전 (Enum/Status)**: 주문·결제·정산·환불·문의 등 전사 공통 상태코드와 한글 라벨 매핑.
4. **화면 코드 통합·폐지 기준**: 단일 정본 기준 유효 화면 코드 및 폐지/통합된 화면 코드 명시.
5. **외부 연동 경계**: 결제(PG)·본인인증·메시지·세금계산서 등 외부 인터페이스 방식.
6. **도메인 간 데이터 조작 금지 및 표준 API Mock JSON 스키마**:
   - 타 도메인 테이블 직접 `insert/update/delete` 금지 (Service/Event 경유).
   - **백엔드·프론트엔드 병렬 개발을 위한 핵심 API 엔드포인트별 요청 파라미터 및 응답 Mock JSON 예시 고정**.

## 3. `docs/contracts/00_ui_system.md` 필수 포함 항목 (Track A / Track B)
1. **Track A (AI 프론트 자체 구현 — 백오피스/어드민)**:
   - **4대 표준 화면 골격(`List-Modal`, `Detail-Form`, `Stats-Dashboard`, `Tabs-Complex`)** 컴포넌트 경로와 슬롯 규격.
   - 검색 필터 배치(최대 3열), 금액 우측 정렬, 상태 배지 컬러 매핑(`대기=amber`, `진행=blue`, `완료=emerald`, `반려/오류=rose`).
2. **Track B (UIX 디자이너 협업 — 유저 프론트/브랜드 화면)**:
   - 시각적 정본은 **UIX 디자이너의 Figma 시안(Figma MCP 연동)**임을 명시.
   - Figma 프레임 명명 규칙(`[<화면코드>] 화면명`) 및 **`Ready for Dev`(디자인 확정)** 상태 게이트 정의.
   - 개발자 AI의 Track B DOM/스타일 임의 변형 절대 금지 규칙.
```

### 3.3 `/doc-update` — PO/PM 정책 변경 스킬 (영향도 스캔 → 패스트트랙 판별 → Git 지시서 생성)

```markdown
---
name: doc-update
description: PO/PM이 신규 설계나 정책·화면 규칙 변경을 안건 단위로 지시할 때, 영향받는 모든 문서 절과 화면 코드 및 변경 등급(Level 1~3)을 먼저 스캔해 보고하고, 승인 후 정본·계산기 일괄 개정 및 Git 내장 변경 지시서(docs/changes/LATEST_TASK.md)를 자동 생성한다.
---

# /doc-update (PO/PM 정책 변경) 실행 절차

## Step 1. 영향도 전수 스캔 및 변경 등급(Fast-Track) 판별 보고
1. PO/PM이 변경할 정책이나 신규 기능을 자연어 안건(주제)으로 지시하면 곧바로 파일을 고치지 않는다.
2. `canon_index.md`, 정본 문서, 도메인 계산기(`engine/`)를 검색하여 아래 표를 먼저 PO/PM에게 보고한다:
   - **변경 등급 판정**:
     - `Level 1 (Full Track)`: 신규 화면 또는 UI+비즈니스 로직 동시 변경 (UIX + 개발 모두 전달)
     - `Level 2 (Logic Fast-Track)`: 화면 UI 변경 없이 수식·비즈니스 규칙만 변경 (**UIX 생략**, 개발 직행)
     - `Level 3 (Micro / Hotfix)`: 단순 문구 수정 또는 긴급 장애 선조치 후 사후 정본 반영
   - **영향받는 정본 문서 및 절/줄 번호** (타 도메인 PM 담당 문서 포함 시 공동 검토 알림 표시)
   - **자동 추출된 영향 화면 코드 목록 (`ADMN-*`, `USER-*`) 및 Track A / Track B 구분**
   - **도메인 계산기(`engine/`) 및 API Mock(`00_domain_contracts.md`) 수정 필요 여부**

## Step 2. 정본 · 계산기 · API Mock 일괄 개정
1. PO/PM이 승인하면 관련 정본 문서 본문을 인라인으로 수정한다.
2. 도메인 계산기 로직이나 API 응답 필드가 바뀌면 `engine/` 시나리오와 `00_domain_contracts.md`의 Mock JSON을 함께 갱신한다.
3. Track A(백오피스) 화면에 대해 PO/PM이 시각적 확인을 요청하면 4대 표준 골격 기반 **1회성 임시 프리뷰**만 생성해 보여준다.

## Step 3. 문서 개정이력(Revision History) 기록 및 색인 갱신
1. 수정된 정본 문서 상단의 `## 문서 개정 이력` 표 맨 아래에 **새 버전 행(버전 · 일자 · 담당 PO/PM · 영향 화면 코드 · 변경 요약)**을 추가한다.
2. `build_canon_index.py`와 `build_screen_digest.py`를 실행해 색인과 요약본을 최신화하고 정적 QA 스크립트를 통과시킨다.

## Step 4. Git 내장 변경 지시서(`docs/changes/LATEST_TASK.md`) 생성 및 커밋 (확장 시 사내 플랫폼 API 호출)
1. **[기본 Core] Git 지시서 생성**: 개발자와 UIX의 로컬 AI가 `sync-spec.sh` 직후 즉시 읽을 수 있도록 `docs/changes/LATEST_TASK.md`에 아래 내용을 자동 기록하고 함께 커밋·푸시한다:
   - **안건 제목 · 정본 버전 · 변경 등급(`L1/L2/L3`) · 영향 화면 코드 해시태그**
   - **[UIX 파트 지시사항]** (`Level 1` & Track B 해당 시): 대상 `USER-*` 화면 코드, Figma 프레임명, 추가/변경할 컴포넌트·상태 배지 명세.
   - **[FE/BE 개발 파트 지시사항]**: 도메인별 수정 대상 화면 코드, 변경된 비즈니스 규칙 요약, 갱신된 API Mock/계산기 시나리오 번호.
2. **[확장 제안 Option] 사내 업무플랫폼 API 연동 시**: `.claude/project-meta.json`에 동기화된 프로젝트 ID 및 부서별 담당자 매핑을 참조하여 사내 업무플랫폼 REST API(`POST`)로 안건과 담당자를 자동 등록한다.
```

```markdown
# /dev-screen (개발자 화면 구현) 실행 절차

## Step 1. 정본·변경 지시서 최신화 및 타겟 컨텍스트 핀셋 로드 (6%)
1. `bash scripts/sync-spec.sh`를 실행해 최신 정본을 동기화하고, `docs/changes/LATEST_TASK.md`(이번 변경 지시서) 및 입력받은 화면 코드를 확인한다.
2. **절대 정본 마크다운 전체를 통째로 읽지 않는다.** 아래 핵심 명세만 핀셋으로 읽는다:
   - `docs/changes/LATEST_TASK.md` (이번 안건의 핵심 변경 요약 및 내 담당 작업 범위)
   - `docs/contracts/00_domain_contracts.md` (도메인 공통 계약 + **API Mock JSON**) 및 `docs/contracts/00_ui_system.md`
   - `docs/canon_index.md`에서 대상 화면 코드가 위치한 정본 문서의 **해당 줄 번호 구간(±50줄)**
   - `docs/digest/<화면코드>_baseline.md` (필드·상태·모달 요약본)

## Step 2. 화면 트랙(Track A vs Track B) 판별 및 UI 소스 결합
1. **Track A (AI 프론트 자체 구현 — `ADMN-*` 백오피스)**:
   - `00_ui_system.md`에 정의된 **4대 표준 화면 골격(`List-Modal`, `Detail-Form`, `Stats-Dashboard`, `Tabs-Complex`)** 컴포넌트를 사용하여 정본 `[B]`의 검색필터·표 컬럼·모달을 배치한다(개발자 임의 레이아웃 창작 금지).
2. **Track B (UIX 디자이너 협업 — `USER-*` 유저 프론트)**:
   - 정본 `[B]`에 기록된 **Figma Node URL**(또는 `[<화면코드>]` 프레임)을 확인하고 **Figma MCP 서버**를 호출하여 Auto Layout, Design Token, 컴포넌트 속성을 직접 읽어온다.
   - 만약 Figma 프레임이 `Ready for Dev` 상태가 아니거나 정본의 필수 필드가 Figma 시안에 빠져 있다면, 임의로 UI를 그려 넣지 말고 즉시 역피드백으로 리포트한다.
   - **절대 금지**: Track B에서 개발자 AI가 UIX 디자이너의 DOM 구조나 스타일 클래스를 임의로 바꾸지 않는다. AI는 오직 Figma/마크업 구조 위에 **데이터 바인딩, API 연동(백엔드 미완성 시 `00_domain_contracts.md`의 Mock JSON 바인딩), 유효성 검증, 비즈니스 로직**만 연결한다.

## Step 3. 미확정 정책 사전 차단(역질문) 및 계층 규격 구현
1. 정본에 정의되지 않은 예외 케이스나 비즈니스 규칙이 발견되면 **임의로 추론해 코딩하지 않고 즉시 멈춘 뒤 `docs/changes/QUESTIONS.md`(확장 시 사내 업무플랫폼 API 댓글)에 `[❓ PO/PM 역질문]`을 기록**한다(테스트는 `markTestIncomplete`로 표기).
2. `Controller` → `Service` → `Repository` → `Model` 계층 규칙을 준수하며, 타 도메인 테이블을 직접 조작하지 않는다.
3. 정본의 핵심 검증 조건과 상태 전이를 검증하는 테스트를 함께 작성한다.

## Step 4. 셀프 대조(`/spec-check`) 및 프리체크(`check.sh`)
1. `/spec-check` 기준에 맞춰 정본 명세 및 Figma 시안 요소 충족 여부를 점검한다.
2. `bash scripts/check.sh`를 실행해 코드 스타일과 병렬 테스트를 통과시킨다.
3. 커밋 메시지에 화면 코드와 정본 버전을 명시한다:
   - 예: `feat(settlement): 정산 수동 조정 라인 등록 검증 보강 (ADMN-SETT-005 · v3.2.32)`
```

```markdown
# /spec-check (정본 대조 검수) 실행 절차

## 1. 실행 모드 판별
- **개발자 로컬 모드**: 현재 브랜치의 변경분(`git diff dev...HEAD` 또는 `LATEST_TASK.md` 대상 화면)을 셀프 대조한다.
- **PO/PM · UIX 총괄 감사 모드**: 지정한 안건/화면 코드 목록, 특정 도메인, 또는 최근 병합 커밋들을 대상으로 정본 저장소(`spec-repo`)와 개발 저장소(`app-repo`) 및 Figma MCP를 직접 대조한다.

## 2. 대조 기준 로드 (문서 정본 + UI 정본)
1. **문서 정본 로드**: 대상 화면 코드(`ADMN-*`, `USER-*`)에 해당하는 `LATEST_TASK.md`, `00_domain_contracts.md`, `canon_index.md` 해당 절 및 최근 `문서 개정 이력`, `digest/<화면코드>_baseline.md`, 도메인 계산기 정답셋(`scenario_amounts.json`)을 읽는다.
2. **UI 정본 로드 (Track별 분리)**:
   - **Track A (`ADMN-*`)**: `00_ui_system.md`의 표준 골격 규격 및 `digest`의 필터·컬럼·모달 정의.
   - **Track B (`USER-*`)**: 정본에 연결된 **Figma MCP 노드**를 조회하여 시안의 입력폼·버튼·상태 배지·텍스트 요소 목록을 가져온다.
3. 이에 대응하는 개발 저장소의 라우트, 컨트롤러, 서비스, 뷰, 테스트 파일을 읽는다.

## 3. 판정 및 리포트 출력 규칙 (문서·코드 임의 수정 금지)
검수 스킬은 파일을 직접 고치지 않고, 아래 **4가지 판정 등급**으로 구분해 근거(정본/Figma 위치 ↔ 코드 파일:줄 번호)를 출력한다.

| 판정 | 의미 | 후속 조치 (담당 파트) |
| :---: | :--- | :--- |
| **`❌ 위반/누락`** | • 정본에 명시된 필드·계산식·상태값·검증 조건이 코드에 빠졌거나 다르게 구현됨<br>• **(Track A)** 표준 화면 골격을 어겼거나 필수 컬럼/모달이 누락됨<br>• **(Track B)** Figma 시안에 있는 UI 컴포넌트·입력창·데이터 바인딩이 실제 뷰 코드에 누락됨 | **개발자 코드 수정 필수** (커밋/병합 차단 사유) |
| **`⚠️ 임의 구현`** | • 정본에는 없는 비즈니스 규칙·상태값·예외 분기가 코드에 임의로 들어가 있음<br>• **(Track B)** UIX 디자이너의 Figma 시안/마크업 구조를 개발자 AI가 임의로 변형함 | **개발자 제거 또는 PO/PM·UIX 사후 승인 요청** |
| **`❓ 정본/시안 미정의`** | • 개발 중 발견된 엣지 케이스로, 정본 문서나 Figma 시안 자체에 정의가 비어 있어 판단이 필요한 항목 (`markTestIncomplete` 처리분) | **`QUESTIONS.md` (확장 시 사내 플랫폼 API) 역질문 등록 ➔ PO/PM 정본 보완** |
```

## 4. 파트별 사람이 지켜야 할 5대 협업 규약 (Human Governance)

다수의 **PO/PM**, **UIX 디자이너**, **개발자(FE/BE)**가 함께 일할 때 파이프라인이 끊기지 않기 위한 핵심 약속이다.

1. **[전 파트 공통] 사람은 ‘안건(주제)’ 단위로 소통하고, 화면 코드(`ADMN-*`, `USER-*`) 매핑은 AI에게 맡긴다**
   - 사람이 수십 개 화면 코드를 외울 필요가 없다. PO/PM이 안건을 지시하면 `/doc-update`가 영향 화면 코드를 자동 추출해 `LATEST_TASK.md`와 개정이력에 태깅하고, 이를 열쇠(Key)로 삼아 Figma 프레임과 Git 커밋이 연결된다.
2. **[PO/PM] 구두 지시 대신 `/doc-update`로 정본과 `LATEST_TASK.md`(변경 지시서)를 Git에 먼저 올린다**
   - 구두나 메신저로만 지시하면 개발자 코드가 `/spec-check`에서 *"정본 위반(`❌`)"*으로 차단된다. 반드시 `/doc-update`로 정본과 `LATEST_TASK.md`를 갱신해 Git에 푸시한 뒤 간단히 공유한다.
3. **[UIX 디자이너] Track B 화면은 Figma 프레임에 `[화면코드]`를 붙이고 확정 시 `Ready for Dev`로 표시한다**
   - 작업 중인 시안을 개발자 AI가 잘못 가져가지 않도록 `Ready for Dev` 상태를 명확히 관리하고, 디자인상 데이터 길이·레이아웃 한계가 보이면 역피드백을 남긴다.
4. **[개발자] 시작은 `sync-spec.sh` + `/dev-screen`, 커밋 전엔 `/spec-check` + `check.sh`, 애매한 정책은 추론 금지(`❓ 역질문`)**
   - `sync-spec.sh`로 `LATEST_TASK.md`를 받아 `/dev-screen`에 읽히고, 정본이나 Figma 시안에 없는 예외 상황은 AI가 임의로 추론하게 두지 않고 즉시 `❓ 역질문`으로 분리한다.
5. **[확장 제안] 사내 업무플랫폼(API)이나 구글 워크스페이스 연동 시에도 ‘복붙 0%’ 원칙을 유지한다**
   - 사내 업무플랫폼을 연결할 때는 초기 1회 동기화한 `project-meta.json`(프로젝트·부서별 담당자 정보)과 경량 API 3종을 통해 로컬 AI가 직접 읽고 쓰게 하여 사람이 중간에서 복사·붙여넣기 하지 않게 한다.
