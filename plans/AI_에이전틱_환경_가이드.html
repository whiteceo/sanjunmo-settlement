AI AGENTIC SDLC METHODOLOGY BLUEPRINT v2.6

AI 에이전틱 개발 · 정합성 검증 표준 방법론

다수의 PO/PM · UIX 디자이너 · 개발자(FE/BE)가 협업할 때 발생하는 단일 정본(SSOT) 이탈과 도메인 간 충돌을 원천 차단하고, 프로토타입 관리 부담 제거 + Figma(MCP) 직결 + 사내 업무플랫폼 피드백 허브까지 하나로 묶은 전사 표준 아키텍처입니다.

📖 먼저 보는 핵심 용어 가이드 (Glossary)

SSOT (단일 정본 · Single Source of Truth)

기획서·정책서가 여러 곳에 흩어지지 않고 오직 정본 저장소(`spec-repo/docs/`)의 문서 하나만 유일한 정답 기준으로 삼는 원칙입니다.

PO / PM (프로덕트 오너 / 매니저)

비즈니스 정책과 화면 기획을 수립하고 단일 정본(SSOT)의 최종 승인 권한을 갖는 기획 책임자 그룹(다수 도메인 PM 포함)입니다.

MCP (모델 컨텍스트 프로토콜 · 외부 도구 직결 통로)

로컬 AI가 UIX 디자이너의 Figma 시안 데이터나 사내 업무플랫폼 게시글을 사람 손 빌리지 않고 실시간으로 직접 읽어오는 연결 규격입니다.

Digest (화면별 1장 요약본)

수천 줄짜리 전체 기획서 중 특정 화면 코드 1개에 필요한 필드·상태값·모달·수식만 1~2장으로 자동 발췌한 AI 전용 요약 카드입니다.

Archetype (표준 화면 골격 4종)

HTML 프로토타입 없이도 백오피스 화면이 일관되게 나오도록 규정한 4가지 표준 레이아웃 틀(목록+모달, 상세폼, 통계, 복합탭)입니다.

Auto Layout & Design Token (자동 배치 & 디자인 변수)

Figma에서 여백·반응형 정렬과 색상·폰트 변수를 규격화해 두어, AI가 눈대중 코딩 없이 디자인을 100% 똑같이 구현하게 하는 설정입니다.

Greenfield / Brownfield (신규 구축 / 레거시 유지보수)

Greenfield는 백지상태에서 새로 짓는 프로젝트, Brownfield는 기존 레거시 코드가 돌아가고 있는 유지보수 프로젝트입니다.

Fast-Track L1~L3 (변경 등급별 경량 경로)

신규/UI변경(L1 풀코스), 화면 변경 없는 수식/로직 수정(L2 UIX 생략), 단순 문구·긴급 장애(L3 선조치 후동기화)로 나눈 처리 경로입니다.

1 토폴로지 비교: 왜 ‘단일 정본(SSOT) + 로컬 스킬’ 구조인가?

왼쪽(각자도생 AI 코딩으로 인한 충돌과 PO/PM 검수 병목)과 오른쪽(단일 정본 허브 + 로컬 스킬 통제)의 구조 비교입니다.

2 컨텍스트 깔때기(Funnel) 도식: 수천 줄 기획서를 어떻게 6%로 줄이는가?

대형 기획서를 통째로 넣지 않고, 화면 코드를 열쇠(Key)로 삼아 해당 화면에 필요한 6% 명세만 핀셋 추출하는 구조입니다.

3 전체 작동 회로도: PO/PM 정책 변경 ➔ UIX·개발 구현 ➔ 분기(역질문) ➔ 검수

다수의 PO/PM, UIX 디자이너, 개발자가 단일 정본(SSOT)과 사내 업무플랫폼을 매개로 순환하는 엔드투엔드 회로도입니다.

4 레거시 역공학 분리기 도식: 정본 없는 유지보수 프로젝트(Brownfield) 온보딩

정본(SSOT)이 없는 유지보수 서비스에서 /doc-init 스킬이 ‘정상 정책’과 ‘의심 하드코딩’을 분리해 정본화하는 원리입니다.

5 화면·프론트엔드 2-Track 도식: 프로토타입 없이 UI 통일성 & UIX(Figma) 직결하기

무거운 HTML 프로토타입 파일을 수작업으로 관리하지 않고, 화면 성격에 따라 Track A(백오피스 표준 골격)와 Track B(UIX 디자이너 Figma MCP 직결)로 이원화합니다.

6 사람(Human) 시점의 파이프라인 전/후 역할 & 사내 업무플랫폼 피드백 허브

다수의 PO/PM · UIX 디자이너 · FE/BE 개발자가 파이프라인 가동 전(Before)과 가동 후(After)에 직접 수행하는 업무와, 휘발되지 않는 사내 게시판형 피드백 채널 구조입니다.

신규 설계 · 정책 변경 전달 및 피드백 수렴 채널 비교 (사내 업무플랫폼 활용 방안)
구분 메신저 단독 (슬랙 / 사내 메신저) 기존 사내 업무플랫폼 (일반 게시판형) 권장: 사내 게시판(경량 개선) + 메신저 알림 하이브리드
다수 인원(N:M:K) 참여 시 문제점 다수의 PM·UIX·개발자가 동시에 대화하면 중요한 정책 합의가 위로 흘러가 3일 뒤 휘발됨 글 작성이 번거롭고, 어떤 화면이 `진행중`인지 `검수완료`인지 상태 추적과 AI 연동이 안 됨 기록·상태·댓글 스레드는 사내 게시판에 영구 보존하고, 메신저는 새 글/댓글 알림용으로만 사용하여 단점 완벽 상쇄
사내 플랫폼 개선 요건 (최소 비용) 해당 없음 현행 유지 시 수작업 부담 큼 1. `[화면코드]` 말머리 태그 필수화
2. 4단계 상태값(`01 접수/질문` · `02 정본검토` · `03 UIX·개발반영중` · `04 검수완료`)
3. 1화면(변경건) = 1게시글 + 댓글(Thread)로 역질문 집중
AI 스킬 연동 방식 Webhook 연동은 쉬우나 스레드 검색·정본 대조가 어려움 수동 작성 • Phase 1 (즉시 적용): `/doc-update`, `/spec-check`가 사내 게시판 등록용 표준 양식을 출력하면 복사·붙여넣기
• Phase 2 (API 1개 추가 후): 로컬 AI가 사내 게시판 REST API로 티켓·역질문 댓글을 자동 등록

7 직관적인 5대 스킬(Skill) 체계 & 프로젝트 유형별 도입 로드맵

누구나 이름만 보고 바로 쓸 수 있는 5개 명령어와 신규(Greenfield)·레거시(Brownfield)·프로토타입 보유 프로젝트별 적용 방법입니다.

01/doc-init
초기 정본 만들기

신규 초안이나 레거시 코드를 읽어 표준 정본(v1.0.0) + 색인 + Digest 요약본 최초 생성

02/doc-rule
공통 규칙 뽑기

도메인 공통 계약·API Mock JSON(00_domain_contracts.md) 및 표준 화면 골격(00_ui_system.md) 추출

03/doc-update
PO/PM 정책 변경

변경 등급(L1~L3) 판별 + 영향 화면 스캔 ➔ 정본·계산기 개정 ➔ 사내 게시판용 개발/UIX 티켓 발행

04/dev-screen
개발자 화면 구현

6% 핀셋 명세 + Track A(표준 골격) / Track B(Figma MCP 직결) 결합 구현 & 미정의 역질문(❓) 분리

05/spec-check
정본 대조 검수

정본(+ Track B Figma 시안)과 코드를 1:1 대조해 ✅ 일치 / ❌ 위반 / ⚠️ 임의구현 / ❓ 미정의 판정
