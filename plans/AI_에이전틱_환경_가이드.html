AI Agentic SDLC Playbook v1.1 (도식화 버전)

AI 에이전틱 개발 · 정합성 검증 환경 가이드

다수의 개발자가 각자 로컬에서 Claude Code로 개발하더라도, 단일 기획 정본(SSOT)을 기준으로 비즈니스 로직 충돌을 예방하고 PO의 수동 검수 병목을 없애는 표준 아키텍처 도식입니다.

1 개념 도식: 왜 이 환경이 필요한가? (Before vs After)

각자 로컬 AI로 코딩할 때 생기는 ‘정본 이탈’과 ‘검수 병목’을 해결하는 구조적 차이입니다.

2 전체 아키텍처 도식: 2개 저장소와 ‘컨텍스트 깔때기(Funnel)’

수천 줄짜리 기획서를 AI에게 통째로 읽히지 않고, 화면 코드를 열쇠(Key)로 삼아 6% 크기의 핵심 명세만 주입합니다.

📐 시스템 연결 구조도 (정본 레포 ⇄ Spec Bridge 깔때기 ⇄ 개발 레포)
🏛️ 정본 저장소 (SSOT) /doc-update
lcampus/sanjunmo-settlement (PO 관리)
1. 정본 마크다운 문서 (docs/) 통합설계서 · 정산 00~04권 + 상단 [문서 개정이력]
2. 백오피스 프로토타입 (40개 화면) prototype_clean/*.html + common-master.js
3. 정산 기준 계산기 (PHP 8.4) engine/php/ + 61건 시나리오 입출력 정답 JSON
💡 PO는 파일을 직접 열지 않고 /doc-update 스킬로 개정·동기화
🌪️ Spec Bridge (깔때기)
scripts/sync-spec.sh (경량 컨텍스트 변환)
화면 코드 (예: ADMN-SETT-005) 입력 시
아래 3가지만 핀셋 추출 (토큰 94% 절감)
① 00_domain_contracts.md
도메인 공통 코드·상태·경계 (1장)
② canon_index.md 발췌 구간
해당 화면의 정본 문서 줄 번호 구간만
③ digest/화면코드.md
필드 ID · 옵션 · 상태값 · 모달 요약본
⇄ sanjunmo/docs/ (.gitignore 로컬 폴더)에 마운트
💻 개발 저장소 (Laravel 13) /dev-screen
lcampus/sanjunmo (개발자 4명 로컬 AI)
1. 루트 지침 (sanjunmo/CLAUDE.md) 계층 규칙(Controller→Service→Repository) 강제
2. 화면 단위 코딩 (/dev-screen) 발췌된 정본+Digest 기준으로만 구현 · 임의 추론 금지
3. 이중 검증 게이트 (커밋 전 필수) /spec-check 대조 + scripts/check.sh (임시 DB 테스트)
🚀 통과한 코드만 dev 병합 → 서버 자동 배포 & 진행률 갱신

3 작동 순서도: PO가 정책을 바꿀 때 & 개발자가 코딩할 때

누가 언제 어떤 스킬을 실행하고, 어디서 브레이크가 걸리는지 화살표 순서도로 확인합니다.

흐름 A PO(white)가 ‘환불 정책’ 등 비즈니스 규칙을 수정할 때 (정본 개정 파이프라인)
STEP 1 · PO 지시 정책 변경 발의

PO가 로컬 AI에게 /doc-update로 수정할 정책 지시

STEP 2 · AI 역추적 영향 화면 전수 스캔

정본·프로토타입·계산기에서 영향받는 절과 화면 코드(ADMN-*, USER-*) 추출 보고

STEP 3 · 일괄 수정 정본·프로토·엔진 개정

PO 승인 시 관련 문서 본문, 프로토타입 양쪽 폴더, PHP 계산기 동시 수정

STEP 4 · 이력 박제 [문서 개정이력] 기록

상단 개정이력 표에 새 버전(v3.2.xx) + 영향 화면 코드 기록 및 색인 갱신

STEP 5 · 자동 전파 개발팀 수정 티켓 발행

dev-progress.php 담당자(박성민·노승원·이응민)별로 수정할 화면·내용 알림 생성

흐름 B 개발자(4명)가 담당 화면을 개발·수정하고 커밋할 때 (구현·검수 파이프라인)
STEP 1 · 작업 시작 화면 코드로 스킬 호출

로컬 AI에 /dev-screen 화면코드 입력

STEP 2 · 핀셋 로드 타겟 명세만 로드

sync-spec.sh 후 해당 화면의 정본 절 + digest + 공통 계약서만 로드

STEP 3 · 정책 판별 미확정 정책 유무 체크

정본에 없는 애매한 규칙이 있는지 코딩 전 판별 (아래 분기 참조)

STEP 4 · 정본 대조 셀프 검수 (/spec-check)

정본 필드·상태·계산식과 내 코드를 대조해 ❌ 위반/누락 0건 확인

STEP 5 · 테스트·커밋 check.sh 통과 후 Push

임시 MySQL 4병렬 테스트 통과 표식 생성 후 화면 코드 적어 커밋

🟢 [STEP 3 분기 — 정본에 명확히 정의된 경우]
➔ Controller → Service → Repository → Model 계층 규칙에 맞춰 즉시 구현 및 Feature 테스트 작성
🟠 [STEP 3 분기 — 정본에 없거나 모호한 예외 케이스 발견 시]
➔ AI 임의 구현 즉시 중단! 테스트에 markTestIncomplete('DECISIONS 대기') 표기 후 PO에게 질문 → PO가 흐름 A(/doc-update)로 정본에 먼저 확정한 뒤 재개

4 확장 도식: 정본이 없는 ‘레거시 유지보수 서비스’는 어떻게 태우는가?

문서가 없는 기존 서비스도 /doc-init(초기 정본 만들기) 스킬로 역추출하여 동일한 파이프라인에 합류시킵니다.

🔄 레거시 역공학 부트스트래핑 (Reverse-Spec Onboarding) 흐름도
PHASE 1 · 레거시 스캔 기존 운영 코드 입력

기획서 없이 돌아가는 레거시 라우트 · 컨트롤러 · 뷰 · DB 스키마

PHASE 2 · 역추출 스킬 /doc-init + /doc-rule

화면 코드 자동 채번 + 표준 3단 템플릿([A]·[B]·[C]) 포매팅 + 공통 계약 추출

PHASE 3 · 분리 판정 정상 정책 vs 의심 로직 분리

• 정상 로직 ➔ 초기 정본 v1.0.0 확정
• 하드코딩/버그 의심 ➔ PO 질문지로 분리

PHASE 4 · 점진적 통제 일상 파이프라인 합류

유지보수 이슈 발생 화면부터 /doc-update ➔ /dev-screen ➔ /spec-check 동일 가동

프로젝트 유형별 AI 에이전틱 환경 도입 비교표
구분 산준모 프로젝트 (현재 진행 중) 신규 구축 프로젝트 (Greenfield) 유지보수 레거시 서비스 (Brownfield)
초기 정본 상태 정본·프로토타입·계산기·색인·Digest 이미 완비됨 코드 0 상태에서 정본부터 작성 시작 정본이 없거나 옛날 문서만 있고 레거시 코드만 돌아가는 상태
첫 단계 (Day 1) /doc-rule로 00_domain_contracts.md 생성 후 바로 /spec-check로 현행 코드 대조 보일러플레이트(CLAUDE.md + 5대 스킬 + check.sh) 복제 후 /doc-init으로 시작 /doc-init (초기 정본 만들기) 실행 → 레거시 코드에서 정본 v1.0.0 + 색인 + Digest 역추출
기존 기술부채 처리 check.sh가 기존 위반 파일은 경고만, 신규/수정 파일만 엄격 검사 첫 커밋부터 기술부채 0건 유지 레거시 전체 리팩토링 없이, 이번에 건드리는 화면부터 점진적 정본화 (Touch-and-Lock)
일상 운영 루프 PO 정책 개정(/doc-update + 문서 개정이력) ➔ 개발자 화면 구현(/dev-screen) ➔ 커밋 전 대조 검수(/spec-check + check.sh) 100% 동일

5 한눈에 보는 5대 스킬 & 5대 필수 규약 요약

팀원들이 북마크해 두고 매일 참고하는 치트시트(Cheat Sheet)입니다.

/doc-init
① 초기 정본 만들기
레거시 코드·초안을 읽어 표준 3단 포맷 정본 v1.0.0 + 색인 + 요약본 최초 생성
🕒 신규/레거시 최초 온보딩 시 (1회)
/doc-rule
② 공통 규칙 뽑기
도메인 간 공유 코드 채번(RH-* 등)·상태값·소속 3분류를 00_domain_contracts.md로 추출
🕒 초기 세팅 & 공통 스키마 변경 시
/doc-update
③ PO 정책 변경
영향 화면 전수 스캔 보고 → 정본·프로토·계산기 일괄 개정 → 개정이력 기록 & 개발팀 티켓 생성
👤 PO (white) 전용 — 정책 개정 시
/dev-screen
④ 개발자 화면 구현
화면 코드 입력 시 해당 정본 구간+Digest만 핀셋 로드해 계층 구현 후 check.sh 실행
👩‍💻 개발자 4명 전용 — 화면 코딩 시
/spec-check
⑤ 정본 대조 검수
정본과 현재 코드를 1:1 대조해 ✅ 일치 / ❌ 위반·누락 / ⚠️ 임의 구현 판정
🔍 개발자(커밋 전) & PO(수시 감사)

⚙️ 시스템이 자동으로 강제하는 것 (Part A)

1. 경량 정본 동기화 (sync-spec.sh)무거운 전체 문서 대신 색인·요약본·계약서·61건 정답셋만 로컬 마운트
2. 프리체크 커밋 가드 (check.sh)변경 파일 Pint + 임시 MySQL 8.4 병렬 테스트 통과 표식 강제
3. 정산 61건 계산기 Parity 검증PHP 8.4 기준 계산기 정답셋과 1원 단위 일치 자동 테스트

🤝 사람이 반드시 지키는 5대 규약 (Part B)

규약 1. 모든 브랜치·커밋에 ‘화면 코드’ 필수 표기(ADMN-SETT-005 · DECISIONS 208)가 모든 자동 매칭의 열쇠
규약 2. [PO] 구두 지시 금지 → /doc-update 선반영구두로만 지시하면 개발자 코드가 /spec-check에서 위반으로 차단됨
규약 3. [개발자] 미확정 정책 임의 구현 금지 & 타 도메인 직접 수정 금지애매한 정책은 PO에게 질문해 정본 확정 후 구현, 남의 테이블은 Service/Event 경유
