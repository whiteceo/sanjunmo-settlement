### 3.3 v1.1(id 50 · 51) 처리 안

전제: 오픈(2026-11-23) 전까지는 개정 이력을 남기지 않고 계속 "최초 제정"으로 둔다(white님 원칙). 운영 사이트가 이 DB를 바로 보므로(1.2), 어떤 안이든 반영 순간 공개 화면이 바뀐다.

**1안. v1.0 하나로 합친다 (권고)**
- 방법: id 50 · 51의 본문(3.1 · 3.2 반영 후)을 id 47 · 48의 `content`에 옮긴다. 47 · 48의 버전 1.0, 공시일, 시행일 2026-11-23, 변경 사유 "최초 제정"을 유지한다. id 50 · 51은 `deleted_at`을 찍어 지운다(11-04에 옛 행을 정리한 방식과 같음).
- 결과: 공개 화면에 v1.0 하나만 남는다. 버전 선택에 "시행 예정 v1.1"과 내부용 변경 사유가 더는 보이지 않는다. 오픈 날 회원은 "최초 제정 v1.0"만 본다.
- 주의: id 49(환불 규정)는 v1.1이 없으니 49만 3.1대로 고친다. 이용약관 v1.1이 "환불 안내"를 바꿨다고 하므로, 49의 환불 문구와 50 본문(환불 조항)이 서로 어긋나지 않는지 합치기 전에 대조해야 한다. 47에 이미 동의한 테스트 회원의 동의 기록은 id 47을 가리키므로 행을 새로 만들지 않고 47을 고치는 편이 동의 연결이 끊기지 않는다(신뢰 3·보통, 동의 테이블 구조는 보지 않음).
- 50 · 51의 작성자(장은영)가 팀 검토용으로 올린 것이므로, 합치기 전에 검토가 끝났는지 장은영 님 쪽에 확인이 필요하다.

**2안. v1.1을 유지한다**
- 방법: 47~49는 시행일만 2026-11-23으로 고치고, 50 · 51은 그대로 두었다가 같은 날 시행.
- 결과: 같은 날(11-23) v1.0과 v1.1이 함께 시행되는 모순이 생긴다. 47~49의 시행일을 앞당기지 않으면 오픈 전에 이미 "개정"이 있었던 모양이 되어 원칙에 어긋난다. 변경 사유 "오픈 전 팀 검토용 …"을 공개용 문구로 고쳐야 한다. 공개 화면의 버전 선택에 두 버전이 계속 보인다.
- 장점: 팀 검토용 원본이 DB에 그대로 남아 비교가 쉽다. 하지만 비교는 로컬 백업(`backup_2026-11-03/` 방식)으로도 할 수 있다.

권고: 1안. 원칙(오픈 전 최초 제정 하나)에 맞고, 지금 운영 화면에 내부용 문구가 노출되는 문제도 함께 없어진다. 실행 전 `backup_2026-11-03/`처럼 id 47~51 현재 행을 SQL로 백업한다.

### 3.4 운영 DB 반영 방법
1.2 결론이 "운영 사이트가 dev DB를 본다"라서 해당 없음. dev DB(`sanjunmo_dev.terms`)를 고치면 sanjunmo.com에 바로 반영된다. 반대로 말하면 dev에서 하는 시험 수정도 운영 화면에 바로 나가므로, 오픈 전에 개발팀에 운영 DB 분리 일정을 확인할 필요가 있다.
