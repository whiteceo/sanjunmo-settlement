## 2. 회원가입 · 실결제 — 두 가지 방식

| | A. white가 테스트 계정을 준다 | B. 내가 직접 가입 · 결제한다 |
| :-- | :-- | :-- |
| 방법 | white(또는 팀)가 본인인증까지 마친 QA_ 회원 2~3개(일반 · 소셜 · 부채 시나리오용)를 만들고 아이디 · 비밀번호를 로컬 파일에 둠. 결제가 필요한 시점에 white가 결제창만 처리하거나, 내가 테스트 카드로 진행 | 가입 화면부터 내가 진행. 본인인증 단계에서 white 휴대폰 인증이 필요하면 그때 white가 직접 처리 |
| 가입 화면 검사 | 가입 화면 · 약관 동의 · 오류 문구는 볼 수 있으나, 끝까지 가는 가입은 계정 수만큼만 | 가입 전 과정을 검사할 수 있으나 본인인증마다 white 손이 필요 |
| 결제 | 토스 테스트 모드라 **내가 테스트 카드로 결제 · 취소 · 환불까지** 진행 | 같음 |
| 장점 | 내일 바로 시작, white 개입이 한 번 | 가입 흐름 결함을 직접 잡음 |
| 단점 | 가입 흐름은 개발팀 SET1 결과에 기대야 함 | 인증 · 결제 때마다 white 대기 |
| 필요한 것 | QA_ 회원 계정 2~3개(인증 완료), 받아도 되는 휴대폰 · 메일 | white 휴대폰 인증 대기(또는 개발팀의 개발 서버 전용 인증 우회 — 요청 중) |

- 권고: **A로 시작하고, 가입 흐름 검사만 B로 1회**(white 인증 1번, 개발팀이 우회를 열어 주면 우회로).
- 금지(두 방식 공통): 실회원 데이터 수정, 실회원 대상 발송.
