### **데이터 필드 사전**

본문에 사용된 데이터 필드 식별자의 의미입니다(가나다 아닌 알파벳순). 표·산식 내 식별자도 본 표로 대조합니다.

| 비즈니스 명칭 | 시스템 식별자 | 설명 및 용도 |
| :---- | :---- | :---- |
| 위탁 정산 기준가 구분 | consignment\_base\_price\_type | 위탁도서 정산 모수 기준 (실결제액 기준: PAID\_AMOUNT [기본값] / 도서 정가 기준: LIST\_PRICE, 계약원장 선택) |
| 도서 기본 할인율 | book\_discount\_rate | 도서 정가 대비 기본 할인율 (0~10% 정수, 도서정가제 상한 10% 하드락) |
| 가격 결정 주체 | price\_owner | 도서 정가 변경 권한 주체 (당사: SELF / 위탁자: CONSIGNOR) |
| 가중치 기본값(초) | default\_weight\_seconds | 러닝타임 0초 강의의 기본 안분 가중치 (기본값: 60초) |
| 개업일자 | start\_dt | 국세청 등록 사업 개업일자 (YYYYMMDD) |
| 갱신 단위 | renewal\_term\_months | 자동 갱신 시 연장되는 개월 수 (화면 표시는 "1년", "2년") |
| 거주자 구분 | is\_resident | 국내 거주자 여부 (기본값 true). false는 비거주자로 1차 오픈 시 계약 심사 차단 또는 수기 정산 대상 |
| 계약 기간 이력 | contract\_terms | 계약 기간 회차 행 테이블 (최초·갱신 회차 보존) |
| 계약 상태 | contract\_status | 작성 중(DRAFT), 계약 중(ACTIVE), 만료(EXPIRED), 중도 해지(TERMINATED) |
| 계약 식별자(ID) | contract\_id | 당사와 권리자 간 체결된 법적 계약의 고유 식별자 |
| 계약 유효 종료일 | end\_date | 요율, 지분율, 약정 등의 유효 만료일 (계약 자체는 현재 종료일(current\_end\_date) 사용) |
| 종료 기준 | end\_basis | 요율·지분율·약정·매핑 행의 종료 판정 방식 (지정일: FIXED\_DATE / 모계약 종료 연동: CONTRACT\_LINKED) |
| 계약 유효 시작일 | start\_date | 계약, 요율, 지분율 등의 적용 시작일 |
| 공급 형태 변경 허용 여부 | book\_supply\_type\_change\_allowed\_yn | 판매 이력 존재 시 도서 공급 형태 변경 가능 여부 (기본 false) |
| 과세최저한 판정 금액 | other\_income\_min\_tax\_amount | 기타소득금액 기준 과세최저한 임계값 (50,000원) |
| 과세표준 | taxable\_base | 원천징수세액 산출의 기준이 되는 세전 소득 금액 |
| 주문 품목 식별자(ID) | order\_item\_id | 주문 내 개별 품목 행의 고유 식별자. 과·면세 분할 승인과 면세 매출 집계의 기준 단위 |
| 과세유형 코드 / 명칭 | tax\_type\_cd / tax\_type | 국세청 API가 반환하는 사업자 과세유형 코드 및 문자열 |
| 과세유형 전환일자 | tax\_type\_change\_dt | 국세청 상태조회 응답상 최근 과세유형 전환일자 |
| 권리자 식별자(ID) | rights\_holder\_id | 플랫폼과 계약된 최상위 정산 주체의 고유 식별자 |
| 권리자 유형 | rights\_holder\_type | 권리자 분류 (일반 권리자: INSTRUCTOR, 위탁자: CONSIGNOR 등) |
| 기 지급 누적액 | cumulative\_paid | 지원금 누계의 공통 필드로 사용하지 않음. 확정·환불 순누계 / 한도 소진액 / 실제 지급 누계로 분리 관리 |
| 확정·환불 순누계 | confirmed\_net\_total | 지원금 확정액에서 환불 공제를 반영한 순누계. 한도 소진액과 구분 |
| 한도 소진액 | cap\_consumed\_amount | 지원금 약정 한도에서 실제로 소진된 누계. 잔여 한도 산정 기준 |
| 실제 지급 누계 | cash\_paid\_total | 세후 실제 송금된 누계. 잔여 한도 산정에는 사용하지 않음 |
| 기타소득 호 구분 | income\_clause | 소득세법 제21조 제1항 각 호 구분 (C05, C15, C17, C19) |
| 다음 갱신 안 함 | renewal\_stop\_yn | 다음 자동 갱신만 중단 (종료일은 유지) |
| 당월 발생액 | accrued\_amount | 당월 정산 연산에서 새롭게 발생한 공급가액 |
| 당월 지원금 확정액 | confirmed\_amount | 지원금 소진 원장(support\_fund\_ledger)에서 5단계 한도 캡 및 환불 공제를 거쳐 확정된 당월 세전 지원금 확정액 (지급 이력상 세후 실제 지급액 paid\_amount와 구분) |
| 대손 처리 플래그 | uncollectible\_status | 미회수 채권의 대손상각 전이 및 파기 보류 상태 플래그 |
| 대상 식별자 | target\_id | 지원금 약정 대상 강의(lecture\_id) 또는 도서 SKU의 식별자 |

| 도서 마스터 | book\_master | 실물 도서 품목의 기본 정보를 관리하는 테이블 |

주민등록번호(고유식별정보), 은행 계좌번호(민감정보) 및 신분증 사본 파일 등 법적 보호 수준이 요구되는 데이터를 취급하므로, 국내 개인정보 보호법 및 국세청 보안 가이드라인에 부합하는 기술적·관리적 보호 조치를 설계합니다.

### **3.1. 수집 및 처리에 대한 법적 근거 명시**

* **주민등록번호 처리의 근거 구조:** 개인정보 보호법 제24조의2 제1항 제1호(법률·대통령령·국회규칙·대법원규칙·헌법재판소규칙·중앙선거관리위원회규칙 및 감사원규칙에서 구체적으로 주민등록번호의 처리를 요구하거나 허용한 경우)에 근거합니다. 산준모의 경우 소득세법 제127조(원천징수의무), 제145조(기타소득 원천징수시기·방법 및 원천징수영수증 발급), 제164조(지급명세서의 제출) 및 제164조의3(간이지급명세서의 제출)에 따라 국세청에 제출하는 법정 서식이 소득자의 주민등록번호 기재를 강제하는 구조를 수집 근거로 삼습니다.
* **암호화 보관 의무:** 개인정보 보호법 제24조의2 제2항에 따라 주민등록번호는 분실·도난·유출·위조·변조 또는 훼손되지 않도록 암호화 조치를 통해 안전하게 보관합니다. 이는 3.2절의 AES-256 적용 근거입니다.
* **목적 범위 제한:** 원천징수 및 지급명세서 제출 목적 외의 용도로는 주민등록번호를 사용하지 않으며, 마케팅·분석·회원 식별 목적의 조회 경로를 시스템에서 차단합니다.
* **인용 시 주의 사항:** 국세기본법 시행령 제68조는 세무공무원의 직무 수행을 위한 근거 조문이므로 민간 원천징수의무자의 수집 근거로 인용하지 않습니다.
* **동의 처리:** 법정 의무 이행 목적의 처리는 정보주체의 별도 동의 없이 허용되나, 권리자 등록 단계의 서비스 이용약관 및 개인정보 처리방침에 해당 근거 조항과 이용 목적(원천세 신고 및 정산금 지급)을 명시합니다.
* **원천징수 비대상 주체의 수집 제한:** 위탁자와 매입처는 원천징수 대상이 아니므로 주민등록번호 수집 근거가 성립하지 않습니다. 사업자등록번호와 계좌 정보만 수집하며, 개인 위탁자 등록 화면에서 주민등록번호 입력 필드를 노출하지 않습니다.

### **3.2. 데이터베이스 내 민감 정보 암호화 적용**

* **양방향 암호화 대상:** 주민등록번호(13자리 전체), 은행 계좌번호, 환급을 위해 수집된 무통장 계좌번호 및 예금주입니다.
* **보안 암호화 알고리즘:** AES-256 양방향 암호화 알고리즘을 적용합니다.
* **키 관리 체계:** 암호화에 사용되는 대칭키는 소스 코드 내에 하드코딩하지 않으며, AWS KMS 또는 전용 보안 자격 증명 관리 도구를 사용하여 격리 통제합니다. 국세청 API 서비스키도 동일한 자격 증명 저장소에서 관리하며 코드·설정 파일에 평문으로 두지 않습니다.

### **3.3. 서버 내 증빙 사본 파일 안전 보관**

* **비공개 버킷 격리:** 업로드되는 신분증 사본, 사업자등록증 사본, 통장 사본, 권리 승계 증빙, 위탁판매 계약서, 분할 지급 스케줄 이체 확인증 파일은 퍼블릭 액세스가 허용되지 않는 프라이빗 스토리지(AWS S3 Private Bucket)에 보관합니다.
* **저장 암호화:** 스토리지 자체에 KMS 기반 서버 사이드 암호화(SSE-KMS, AES-256)를 활성화하여 파일 유출 리스크를 차단합니다.
* **임시 호출 보안:** 어드민 화면에서 담당자가 증빙 서류 뷰어 아이콘을 클릭하여 대조할 때만, 백엔드 서버가 실시간으로 5분 내외의 만기 주기를 가지는 임시 서명 URL(Presigned URL)을 발급하여 화면에 임시 렌더링하고 소멸시킵니다.
* **API 응답 스냅샷 보관:** 국세청 API 응답 원문(JSON)은 개인정보가 아닌 사업자 정보이나, 대표자명이 포함되므로 동일한 프라이빗 버킷에 저장하고 감사 추적 대상으로 관리합니다.

### **3.4. 어드민 화면 기본 마스킹 및 감사 로그 통제**

* **기본 마스킹 처리:** 권리자 계약 원장 및 정산 관련 목록·상세 화면에서 주민등록번호 뒷자리와 은행 계좌번호 일부는 기본적으로 별표 마스킹 처리하여 시각 노출을 통제합니다.
* **마스킹 해제 권한 제어:** 마스킹 해제는 정산 권한이 할당된 전용 재무 운영자 그룹(RBAC)에게 노출되는 열람 아이콘 클릭 시 동작합니다.
* **감사 로그 적재:** 담당자가 마스킹 해제 버튼을 클릭하거나 증빙 사본 파일 다운로드를 실행할 때, [민감 정보 열람 사유 입력 팝업, ADMN-USER-007]을 호출하여 최소 10자 이상의 구체적인 열람 사유를 수기 입력하게 통제합니다. 해당 액션은 시스템 감사 로그 테이블(ADMN\_AUDIT\_LOG, ADMN-CONF-010)에 기록됩니다.
* **자동 재마스킹:** 마스킹 해제 후 부록 B의 민감 정보 재마스킹 시간(pii\_unmask\_ttl\_seconds)이 지나면 화면 값을 다시 마스킹합니다. 재열람하려면 열람 사유 입력(ADMN-USER-007)을 다시 거칩니다.

### **3.5. 법정 보존 기한 및 파기 정책**

> 개인정보별 수집 근거, 보존기간, 기산점, 접근권한, 파기 방법 및 예외 처리는 별도 보안·개인정보 처리 설계서에서 관리합니다. 정산 원장의 보존기간을 이유로 주민등록번호, 신분증, 주소, 연락처, 대표자명 등 개인정보의 보존기간을 일괄 연장하지 않습니다. 계약서·이체 확인증 등 증빙의 보존과 그 안에 포함된 개인정보의 처리 기준도 항목별 근거에 따라 관리합니다.
>
> 개인정보 필드 파기와 정산 원장 보존은 별도 작업으로 처리합니다. 개인정보를 파기하더라도 보존해야 하는 금액, 원거래 참조, 조정 내역 및 감사 이력의 정합성은 유지합니다. 식별자 치환·가명처리만으로 파기가 완료된 것으로 보지 않으며, 파기 대상 정보는 승인된 방법으로 복구 불가능하게 처리하고 유예·승인·실행·실패 이력을 남깁니다.

정산 문서에서 상세 개인정보 규격을 이관할 때에는 이관 대상 문서와 항목을 참조 위치로 남깁니다. 본 개정 시점의 이관 대상은 계층 1 항목(주민등록번호, 신분증 사본, 통장 사본, 거주지 주소, 개인 연락처)과 계층 3 항목이며, 도착 문서는 별도 보안·개인정보 처리 설계서입니다. 해당 설계서의 문서 식별자·버전·절 번호는 설계서 확정 시 기재할 자리표시자이며, 확정 전에는 이 문단이 참조 위치를 대신합니다.

보존 기한을 단일 5년으로 통합하지 않고, 데이터 성격별 3계층 분리와 개인정보 파기·원장 보존의 분리 원칙을 함께 적용합니다.

* **파기 원칙:** 보유기간의 경과, 처리 목적 달성 등으로 개인정보가 불필요하게 되었을 때 지체 없이 파기합니다(개인정보 보호법 제21조 제1항 본문). 다만 다른 법령에 따라 보존해야 하는 경우는 파기 예외이며(같은 항 단서), 이때 해당 개인정보 또는 개인정보파일은 다른 개인정보와 분리하여 저장·관리합니다(같은 조 제3항). 파기 시 복구 또는 재생되지 않도록 조치합니다(같은 조 제2항).
* **계층 1 (개인정보 및 고유식별정보) — 별도 설계서 이관 대상:** 주민등록번호, 신분증 사본, 통장 사본, 거주지 주소, 개인 연락처입니다. 아래 보존기간과 기산점은 이관 전 기준선이며, 항목별 상세 규격은 별도 보안·개인정보 처리 설계서에서 관리합니다. 이관 전 기준선은 국세기본법 제85조의3 제2항에 따라 해당 국세의 법정신고기한이 지난 날부터 5년입니다.
* **계층 2 (계약서 원본 및 회계 원장):** 계약서 원본(PDF), 요율 및 지분율 변경 이력, 정산 명세서 원장, 원천세 신고 이력, 이체 확인증, 국세청 API 조회 이력, 위탁판매 계약서 및 수취 계산서 이력입니다. 상법 제33조 제1항 본문에 따라 상업장부와 영업에 관한 중요서류는 10년 보존하며, 전표 또는 이와 유사한 서류는 같은 항 단서에 따라 5년 보존합니다. 상업장부의 보존기간 기산점은 그 폐쇄한 날입니다(같은 조 제2항). 전산정보처리조직에 의한 보존이 허용되므로(같은 조 제3항) 전자 보관을 원칙으로 합니다.
* **파기와 보존의 충돌 해소 규칙:** 계층 1의 파기와 계층 2의 보존은 동일 레코드에 대한 상반된 요구가 아니라 필드 단위로 분리 적용합니다. 계층 1 기한 경과 시점에 개인 식별 필드(주민등록번호, 신분증 사본, 주소, 연락처)만 파기하고, 정산 원장과 신고 이력은 내부 대체키인 권리자 식별자(rights\_holder\_id)와 비식별 표시명(성명 이니셜 \+ 계약 ID)으로 전환하여 잔존 보존합니다. 파기 실행 시 원장 레코드를 삭제하거나 금액 필드를 비우는 처리는 금지합니다.
* **파기 실행 순서:** 개인정보 필드 파기와 정산 원장 보존은 별도 배치로 분리합니다. 개인정보 파기 배치는 해당 개인정보 항목별 수집 근거와 보존기간을 기준으로 실행하며, 정산 원장의 보존기간을 이유로 개인정보 파기 예정일을 일괄 연장하지 않습니다. 정산 원장·증빙 배치는 계층 1과 계층 2의 보존기간 중 긴 쪽을 만족한 뒤 실행하고, 두 기산점(법정신고기한이 지난 날 / 장부 폐쇄일)이 다르므로 라인별 파기 예정일을 개별 산출합니다.
* 파기 대상 필드와 잔존 필드의 목록은 개인정보 파기 필드 매핑(pii\_destruction\_field\_map) 설정 테이블로 관리하여, 법령 변경 시 코드 수정 없이 대응합니다.
* 파기 실행 결과는 파기 대상 건수, 파기 필드, 잔존 원장 건수를 함께 시스템 감사 로그(ADMN-CONF-010)에 기록합니다.
* **계층 3 (파기 예외 대상):** 미상계 선급금 잔액이 존재하는 레코드, 대손 처리 플래그(uncollectible\_status)가 설정된 채권 레코드, 미소진 지원금 한도가 남은 매출연동(R/S)형 약정 레코드, 진행 중인 세무조사·소송·이의신청과 관련된 레코드는 파기 대상에서 제외(파기 보류 플래그(destruction\_hold) \= true)하고, 개인정보 보호법 제21조 제3항에 따라 분리 저장합니다.
* **파기 스케줄러 실행 규격:** 스케줄러는 파기 대상 후보를 먼저 목록으로 산출하여 재무 담당자의 확인 및 승인을 거친 뒤 실행하며, 무인 자동 삭제는 적용하지 않습니다.

## **제16장. 백오피스 메뉴 구조 및 화면 명세**

### **16.1. 화면 목록 요약**

* **ADMN-INST-001 (권리자 계약 원장 / 설정):** 권리자 기본 정보(계약 당사자와 2계층 수취인 — 공동 서명 수취인 · 상속 승계인도 권리자로 등록해 계약에 연결), 권리자 유형(rights\_holder\_type: 권리자·위탁자), 세무 유형(국세청 API 응답 기반 자동 설정), 저작자 본인 여부(payee\_is\_author), 주된 업무 외 노무 활용 여부(main\_work\_external\_labor), 소득 구분 상위 축(income\_category) 및 기타소득 호 구분(income\_clause), 계약 유형, 요율 라인 버전 관리(요율 행 유형(rate\_type) 구분 포함), 인세 조건, 매절 금액 및 소득 구분, 위탁 수수료율 및 위탁 수수료 수취 방식(consignment\_fee\_type), 매출연동(R/S)형 지원금 약정(한도 유형(cap\_type), 총 한도 금액(total\_cap\_amount), 지원금 요율(요율 라인 rate\_type \= SUPPORT 행), 요율 기준 모수(rate\_basis), 정산 범위(settlement\_scope), 약정 대상, 종료 기준(end\_basis), 약정금 종료 처리 정책(on\_termination\_policy)), 선급금(선급금 세무 처리 유형(prepayment\_tax\_type), 상계 대상 수취인 식별자(offset\_payee\_id, 원 권리자 자동 고정)) 및 월 최저보장 보전금(MMG) 특약, 최소 정산 지급 기준액(min\_payout\_limit)·최소 정산 청구 기준액(min\_claim\_limit), 환급 부담 방식(refund\_promo\_burden\_type) 등록. 사업자등록 확인 이력 서브 탭 포함(제17장).
* **계약 종료·승계 연계:** 계약 종료일 입력 시 잔여 매핑 강의 건수를 경고로 노출하며, 계약 종료 후에도 판매·이용을 계속하기 위해 유효 계약이 필요한 매핑 중 승계 계약 또는 매핑 종료 처리가 지정되지 않은 매핑이 있으면 종료 확정을 차단합니다(5.4절). 종료 후 판매·이용을 계속하지 않는 매핑에는 승계 계약을 일괄 요구하지 않습니다.
* **ADMN-INST-002 (약정금 마일스톤 검수 및 승인 원장 / 검증):** 비정기 약정금 및 매절 대금 이행 조건 검수(증빙 첨부/수기 소명), 매출연동(R/S)형 지원금 약정 체결 1회 검수, 소득 구분 지정 확인, 지원금 필수값 확인 게이트, 사업자 상태 확인 게이트, 귀속월 확정, 당월 정산서 이관 승인, 승인 직후 정산서 반영 알림 모달(배치 실행 후 마감 전 월은 해당 권리자 자동 재연산 후 지급 예정액 변경 전·후, 배치 전 월은 다음 배치 반영 예정, 제1권 7.2절) (자금 출금 기능 일체 배제).
* **ADMN-SETT-001 (상품별 권리자 매핑 / 설정):** 강의 및 도서 상품 식별자(SKU) 단위 1계층 권리자 지분율 배치 편집, 유효일자 기반 이력 관리, 합계 100.00% 트랜잭션 저장(정산 대상 SKU 한정), 매입 재판매·부속 도서의 자사 권리자 100% 자동 매핑 결과 조회. 화면 진입 및 로드는 상품(강좌) 단위이되 저장은 강의(lesson) 행 단위임을 규격에 명시합니다(개발 오해 방지). 본 명세에서 강좌(상품)와 강의(lesson)는 상위–하위 관계의 서로 다른 단위로 구분하며 혼용하지 않습니다. 권리자 행마다 계약 선택 필드(필수값)를 추가하며, 계약 선택 드롭다운은 유효 계약 마스터(active\_contracts)에 등록된 해당 권리자의 유효 계약으로 한정합니다. 선택된 계약에 대해서는 계약 합의 당사자 일치 원칙(4.1절)의 검증을 그대로 승계합니다. 편집 진입점 단일화(4.3절)에 따라 본 화면이 1계층 매핑의 유일한 쓰기 진입점입니다. 기간 구간별 합계 100.00% 검증, 지분율 0 초과·소수점 둘째 자리 제약, 종료 기준(계약 종료 연동/지정일) 선택, '계약 기간 불일치' 표시 및 일괄 동기화, 변경 사유 필수 입력, 지원금 약정 연동 경고를 제공합니다(4.3절). 별도 승인 단계는 두지 않습니다. 모든 판정은 서버 측 공통 검증 모듈을 따릅니다(제1장).
* **강의 등록 화면 정산 연계:** 강의 등록 화면에는 지분 매핑 편집 기능을 두지 않고, '정산 매핑 미완료' 배지와 상품별 권리자 매핑(ADMN-SETT-001) 딥링크만 배치합니다(편집 진입점 단일화, 4.3절).
* **ADMN-SETT-002 (월간 정산 및 집행 / 집행):** 통합 연산 엔진(1\~11단계) 배치 실행, 배치 이후 승인·확정으로 자동 재연산된 권리자 목록과 사유 표시(약정금 승인 ADMN-INST-002 · 합격 환급 확정 ADMN-SETT-006, 제2권 10.1절), 통합 정산서 생성, 정산 마감 확정(Locked \= True) 확정, 대량이체 지급 엑셀 생성 · 결과 파일 대사(권리자 정산금·비정기 약정금·매절 대금·위탁 정산금 한정, 제1장 단일 게이트웨이 범위와 동일), 수취인별 지급 라인 노출, 정산 입력 구분(Pipeline)별·라인별 분리 표기(온라인 강좌 수익배분(Pipeline 1.1) / 자사 발행 도서 인세(Pipeline 2.1) / 위탁 도서 판매대금 정산(Pipeline 2.2) / 매출연동 개발지원금(Pipeline 5.1)), 지원금 소진 현황 노출, 2채널 전자(세금)계산서 발행 요청 · 제출 · 홈택스 대사 현황 추적(제2권 제9장), 수취 증빙 상태 추적 (자금 출금 단일 게이트웨이). 이월 목록·상세 모달에는 원천징수 전 기초금액, 예상 원천세, 예상 실지급 판정액, 이미 세무 처리된 지급대기액, 지급·청구 방향, 이월 사유 및 지급 상태를 함께 표시하고, 총액 선택 시 상세 모달에서 계약·수취인·입력 구분·원거래·구성요소·세무 및 증빙 상태·상계 범위·예약·지급 이력을 확인하도록 합니다(7.4절).
* **ADMN-SETT-003: 결번.** 초기 설계 단계에서 '정산 요율 관리’로 배정되었으나 요율 라인 버전 관리 기능이 ADMN-INST-001로 통합되면서 사용하지 않게 된 번호입니다. 신규 화면에 재사용하지 않고 결번으로 영구 보존하여, 기존 화면설계서·API 명세·QA 문서의 번호 참조가 어긋나지 않도록 합니다. 이 처리는 확정 결정 사항입니다.
* **ADMN-SETT-004 (PG 정산 원장 대사 / 검증):** 결제대행사(PG) 원장과 자체 결제 데이터베이스 1대1 대사, 차이 원인 코드 분류 및 소명 승인 통제, 미분류 건수 및 전사 총액 차액의 이원화 임계값 판정. 또한 통합 주문·배송 관리(ADMN-ORD-001/002)의 실결제금액(paid_amount, 쿠폰·포인트 차감 후) 및 통합 환불 심사(ADMN-RFD-002)의 PG 취소·수취계좌 현금환불 확정 내역과 PG 정산 원장을 결제수단 유형(카드·계좌이체·가상계좌·간편결제·휴대폰)별로 1:1 교차 검증한다.
* **ADMN-SETT-005 (정산 수동 조정 / 집행 보조):** 당월 수동 조정 등록, 마감 후 전기오류수정을 위한 전월 정정 라인 등록(원 발생 귀속월(origin\_month)과 반영 기준월(applied\_month) 분리), 세전·세후 계정 간 대체 전표 등록, 지원금 이행률 정산(PRO\_RATA) 등록.
* **ADMN-SETT-006 (합격 환급반 관리 / 운영):** 환급 조건 검수 및 환급 확정, 계약별 부담 방식(A/B/C)에 따른 정산 연동, MMG 중복 발생 플래그 노출. 정산 반영 확정 직후 알림 모달(배치 실행 후 마감 전 월은 옵션 B·C 분담 권리자 자동 재연산 결과, 옵션 A는 강사 정산 영향 없음, 제1권 15.3절).
* **ADMN-SETT-007 (수취인 분할 지분 설정 / 설정):** 계약·권리자 단위 2계층 수취인 분할 비율 등록(수취인은 권리자 계약 원장에서 그 계약에 연결된 권리자 중에서만 선택), 유효일자 기반 이력 관리, 권리자 기준 합계 100.00% 트랜잭션 저장, 수취인별 세무 유형 조회. 1계층 지분 편집(ADMN-SETT-001)과 물리적으로 분리하여 총합 검증 단위 혼동을 방지합니다. 선급금 원장이 종결되지 않은 계약에는 분할 비율을 저장할 수 없습니다(5.3절 상호 차단).
* **수취인 승계:** 수취인의 사망·상속 등으로 권리가 승계된 경우, 승계인을 권리자 원장에 권리자로 등록해 계약에 상속 승계인으로 연결하고, 승계 확정일 이후 발생분부터 승계인 수취인(payee)을 적용하고 그 이전 발생분의 환불 공제는 스냅샷 비율(원 결제 시점 수취인)을 따릅니다. 저작자 본인 여부(payee\_is\_author) 등 지위 플래그의 전환 시점은 승계 확정일로 고정합니다.
* **ADMN-SETT-008 (사업자등록 확인 이력 / 검증):** 국세청 API 조회 이력 전수 목록, 과세유형 변경 감지 목록, 폐업·휴업 감지 목록, 일괄 재조회 실행, 조회 실패 재시도 큐 관리. 조회 대상에 권리자·위탁자·매입처를 모두 포함합니다. 상세 규격은 제17장을 따릅니다.
* **ADMN-SETT-009 (내부 정산 조회 / 조회 전용):** 자사 매출 라인(일반 상품 판매매출(Pipeline 2.3))과 권리자 지급 라인을 함께 조회하는 뷰 전용 화면. 연산 및 원장은 단일 체계를 유지하며, 대량이체 실행 등 자금 집행 기능은 일체 배제합니다(ADMN-SETT-002와의 권한 분리). 상세 규격은 18.4절을 따릅니다.
* **ADMN-SETT-011 (물류비 대사(3PL) / 검증):** 월 1회 3PL 수수료 명세서를 업로드해 주문/배송(ADMN-ORD-002)의 출고·송장과 대사한다(매칭 키: 송장번호 → 주문번호 → 수령인·출고일). 불일치(3PL만 존재·DB만 존재·수량·단가 차이)는 처리 결과(승인 지급·차감 요청·차월 이월)와 메모 없이 종결할 수 없다. 배송비·반품 대사(고객 결제 배송비 vs 3PL 청구, 반품 귀책은 CS 판정)와 도서 매입 계산서 대조(입고 수량 × 사입 원가 vs 수취 면세 전자계산서, 수취 상태 4종)를 함께 둔다. 물류비 대사 완료는 ADMN-SETT-002 마감의 선행 조건이 아니며, 3PL 물류비와 도서 매입 대금은 대량이체 지급 리스트에 넣지 않고 회계 시스템 AP 결제로 지급한다. 번호는 16.2절 규칙(최대 번호 + 1)에 따라 부여했고, ADMN-SETT-010은 사용하지 않는다(원천세·지급명세서 산출물은 ADMN-SETT-009의 내부 기능).
* **ADMN-VEND-001 (거래처 관리 / 설정):** 권리자 계약 원장에 올리지 않는 거래 상대방(도서 · 상품 매입처, 물류 대행사 3PL, 이후 공급 파트너)을 등록한다. 거래처 유형은 운영 중 추가하는 기준정보이며 유형마다 거래 조건 양식(매입 공급률 · 결제 조건 / 물류 건당 단가 · 반품 회수 · 보관료)과 수취 증빙(면세 계산서 / 세금계산서)이 정해진다. 국세청 상태조회 후 거래를 시작하고 폐업 사업자는 거래 중으로 둘 수 없다. 삭제 없이 거래 중지로 관리한다. 도서 공급 원장 · 일반상품 · 물류비 대사(ADMN-SETT-011) · 외부 계정 소속(ADMN-CONF-005)이 이 원장을 참조하며, 대금은 회계 시스템 AP 결제로 지급한다(대량이체 지급 리스트 미포함).
* **ADMN-BOOK-001 (도서 공급 원장 / 설정):** 도서 마스터의 도서 공급 형태(book\_supply\_type) 등록 및 조회, 도서 정가 이력(book\_price\_history) 및 가격 결정 주체(price\_owner) 관리, 매입처 선택(거래처 마스터 suppliers 등록은 거래처 관리 ADMN-VEND-001), 위탁 도서 목록 및 재고 회수 조건 관리, 정산 대상 여부(settlement\_required\_yn) 파생 결과 노출, 공급 형태 변경 시 판매 이력 유무 검증. 접두사는 도서 유통이 강의·정산과 독립된 도메인임을 반영하여 BOOK으로 도입했으며, 번호는 해당 접두사의 첫 화면이므로 001입니다.
* **ADMN-USER-007 (민감 정보 보관·열람 통제 / 통제):** 암호화 보관된 민감 정보(권리자·환급 수취인·환불 수취인의 실명 계좌, 주민/사업자등록번호 등)의 열람을 통제한다. 마스킹 해제 및 증빙 사본 다운로드 시 최소 10자 사유 입력 팝업을 강제하며, 휴대폰 결제 익월 환불·가상계좌 환불의 현금환불 수취계좌도 이 통제 아래 암호화 보관한다.
* **ADMN-CONF-010 (시스템 감사 로그 / 통제):** 민감 정보 열람, 1계층·2계층 지분율 변경 이력(변경 전·후 값, 작업자, 시각, 변경 사유), 수기 검수, 정산 수동 조정 승인, 계정 간 대체, 개인정보 필드 파기 이력, 국세청 API 조회 및 과세유형 자동 변경 이력, 도서 공급 형태 변경, 지원금 약정 상태 전이(COMPLETED ↔ ACTIVE) 및 한도 복원 이력, 운영자·파트너 계정의 접근·권한 변경·파일 다운로드 이력 전수 보존. 화면설계서 v12의 이력/보안 로그(ADMN-CONF-006)는 이 화면으로 통합하고 CONF-006은 결번으로 둔다.

### **16.2. 화면 번호 운영 규칙**

* 결번은 재사용하지 않습니다. 기능이 폐기되거나 타 화면으로 통합된 번호는 결번으로 표기하고 통합 대상 화면 식별자를 함께 기록합니다.
* 신규 화면은 해당 접두사의 최대 번호 \+ 1로 부여합니다. ADMN-SETT-008과 ADMN-SETT-009는 이 규칙에 따라 부여했습니다.
* **신규 접두사 부여 기준:** 기존 접두사(INST, SETT, USER, CONF)의 의미 범위를 벗어나는 독립 도메인이 추가되는 경우 신규 접두사를 부여합니다. 도서 유통은 설정·검증·집행 어디에도 일대일로 대응하지 않고 상품 마스터 성격이 강하므로 BOOK을 도입했습니다. 접두사 도입은 역할 기반 접근 제어(RBAC) 권한 정의서의 그룹 신규 정의를 동반하므로 임의로 늘리지 않습니다.
* 화면 번호는 화면설계서, API 명세, QA 테스트 케이스, 역할 기반 접근 제어(RBAC) 권한 정의서에서 공통 조인 키로 사용되므로, 번호 변경은 4개 산출물 동시 개정을 전제로만 허용합니다.

## **제17장. 국세청 사업자등록정보 오픈API 연동 규격**

### **17.1. 연동 목적 및 판정 권한의 배분**

* 당사는 권리자의 부가가치세 과세유형과 사업자 상태를 직접 판정하지 않습니다. 과세유형의 결정·통지 주체는 국세청이고, 간이과세 여부는 직전 연도 공급대가라는 당사가 알 수 없는 정보로 결정되기 때문입니다. 국세청 사업자등록정보 오픈API는 진위·사업자 상태·과세유형 확인 자료이며, API 과세유형만으로 소득 구분·원천징수·증빙 의무를 모두 확정하지 않습니다. 상태 코드와 과세유형 코드를 구분하고, 내부 파생 필드를 API 원응답 필드처럼 설명하지 않습니다. 따라서 시스템은 다음 원칙을 따릅니다.
* 당사의 역할은 확인과 보존입니다. 국세청 오픈API 응답값과 제출된 사업자등록증의 일치를 확인하고, 응답 원문을 계약 원장에 스냅샷으로 남깁니다.
* 담당자는 과세유형을 수기로 선택하지 않습니다. API 응답값을 시스템이 매핑하여 수취인 과세유형(payee\_tax\_type)과 세금계산서 발급 가능 여부(tax\_invoice\_eligible\_yn)를 자동 설정하며, 해당 필드는 화면에서 편집 불가(읽기 전용)로 노출합니다.
* API 응답값과 사업자등록증이 불일치하면 저장을 차단하고 정정된 사업자등록증 제출을 요청합니다. 둘 중 하나를 담당자 판단으로 채택하는 경로를 두지 않습니다.
* 세무조사 대응 시 당사의 선관주의 입증 자료는 조회 이력과 응답 스냅샷입니다. 이것이 API 연동의 실질적 목적입니다.
* **적용 대상 확대:** 권리자에 한정하지 않고 위탁자와 매입처(suppliers)를 모두 조회 대상에 포함합니다. 폐업 사업자로부터는 계산서를 수취할 수 없으므로 발주·위탁 등록 전 확인이 필요합니다.

### **17.2. 대상 API 규격**

공공데이터포털 ‘국세청\_사업자등록정보 진위확인 및 상태조회 서비스’(https://www.data.go.kr/data/15081808/openapi.do)를 사용합니다. 아래 규격은 공공데이터포털 및 구현 사례 문서에서 확인한 내용입니다.

* **진위확인 API:** POST https://api.odcloud.kr/api/nts-businessman/v1/validate?serviceKey={키}&returnType=JSON
* **상태조회 API:** POST https://api.odcloud.kr/api/nts-businessman/v1/status?serviceKey={키}&returnType=JSON
* **공통 호출 규격:** GET이 아닌 POST 전용입니다. 서비스 키(serviceKey)와 반환 형식(returnType)은 URL 쿼리스트링에 두고, 사업자등록번호 등 나머지 파라미터는 반드시 요청 바디(JSON)에 담습니다. 1회 호출당 최대 100건까지 배열로 요청할 수 있습니다. 사업자등록번호는 하이픈 없는 숫자 10자리, 개업일자는 하이픈 없는 YYYYMMDD 형식입니다.
* **진위확인 요청 항목:** 사업자등록번호(b\_no, 필수), 개업일자(start\_dt, 필수), 대표자성명(p\_nm, 필수. 외국인은 영문명), 대표자성명2(p\_nm2, 외국인의 한글명), 상호(b\_nm), 법인등록번호(corp\_no, 13자리), 주업태명(b\_sector), 주종목명(b\_type). 필수가 아닌 항목을 비워 호출할 때는 키를 생략하지 않고 빈 문자열(“”)로 포함시켜야 합니다. 상호는 ‘(주)’, ‘주식회사’ 표기 차이와 앞뒤 공백을 무시하고 검색되며, 업태·종목은 모든 공백을 무시하고 검색됩니다.
* **진위확인 응답 해석:** 요청 항목이 전부 일치하면 해당 사업자의 상태조회 결과가 함께 반환됩니다. 불일치하면 확인할 수 없다는 메시지가 반환됩니다. 즉 진위확인 API는 1회 호출로 진위와 상태를 동시에 얻을 수 있는 구조입니다.
* **상태조회 요청 항목:** 사업자등록번호(b\_no) 배열(사업자등록번호 목록)만 필요합니다.
* **상태조회 주요 응답 항목:** 납세자 상태(b\_stt: 계속사업자 / 휴업자 / 폐업자), 사업자 상태 코드(b\_stt\_cd), 과세유형 명칭(tax\_type), 과세유형 코드(tax\_type\_cd), 폐업일자(end\_dt), 단위과세전환폐업여부(utcc\_yn), 최근 과세유형 전환일자(tax\_type\_change\_dt), 세금계산서 적용일자(invoice\_apply\_dt), 직전 과세유형(rbf\_tax\_type).
* **응답 필드 검증 상태:** 과세유형 판정은 과세유형 코드(tax\_type\_cd)를 기준으로 하며, 과세유형 명칭(tax\_type)은 표시·이력 보존용으로만 사용합니다. 코드값은 공공데이터포털 명세 기준 01(일반과세자), 02(간이과세자), 03(과세특례자), 04(면세사업자), 05(수익사업을 영위하지 않는 비영리법인이거나 고유번호가 부여된 단체, 국가기관 등), 06(고유번호가 부여된 단체), 07(간이과세자 — 세금계산서 발급사업자)입니다. 국세청에 등록되지 않은 번호는 tax\_type\_cd와 b\_stt\_cd가 빈 값으로 반환되고, tax\_type에 안내 문장이 담깁니다. 구현 착수 시 실제 응답 1건으로 코드값을 대조한 뒤 프로덕션에 배포합니다.

### **17.3. 과세유형(tax\_type) 응답값과 매트릭스 케이스 매핑**

API가 반환하는 과세유형 문자열을 세무 판정 매트릭스의 케이스로 변환하는 매핑 테이블(nts\_tax\_type\_map)을 설정 테이블로 관리합니다. 코드에 문자열을 하드코딩하지 않습니다.

* **tax\_type\_cd \= 01 (부가가치세 일반과세자)** → 수취인 과세유형(payee\_tax\_type) \= GENERAL, 세금계산서 발급 가능 여부(tax\_invoice\_eligible\_yn) \= true, 매트릭스 TX-07 (법인·단체가 인세를 수취하는 라인은 TX-09).
* **tax\_type\_cd \= 02 (부가가치세 간이과세자)** → SIMPLIFIED\_RECEIPT, 세금계산서 발급 가능 여부(tax\_invoice\_eligible\_yn) \= false, 매트릭스 TX-05 (간이과세자 — 영수증 발급 대상). 부가가치세 미가산, 영수증 대사 경로.
* **tax\_type\_cd \= 07 (부가가치세 간이과세자(세금계산서 발급사업자))** → SIMPLIFIED\_INVOICE, 세금계산서 발급 가능 여부(tax\_invoice\_eligible\_yn) \= true, 매트릭스 TX-06 (간이과세자 — 세금계산서 발급사업자). 세금계산서 권리자 발행 · 제출 경로.
* **tax\_type\_cd \= 04 (부가가치세 면세사업자)** → EXEMPT, 세금계산서 발급 가능 여부(tax\_invoice\_eligible\_yn) \= false (계산서 대상), 기본 매트릭스 TX-08. 단, 수취인이 법인(`corp_no` 보유)인 경우 인적용역 면세(개인 한정)가 적용되지 않으므로, 저작권 인세·매절 대금 수취 라인은 후보 케이스 `TX-09`를, 면세 교육용역 요건 미충족 강의 R/S·약정금·개발지원금 수취 라인은 후보 케이스 `TX-07`을 부여하되 판정 상태(`tax_decision_status`) \= `PENDING_REVIEW`로 격리하여 과세사업 겸영 등록 및 세금계산서 발급 가능 여부를 확인합니다(`→ [SSOT: 11.1·11.2·11.3절]`).
* **tax\_type\_cd 빈 값 (국세청에 등록되지 않은 사업자등록번호)** → 등록 차단. 저장을 거부하고 사업자등록증 재확인을 요청합니다.
* **tax\_type\_cd \= 05 또는 06 (수익사업을 영위하지 않는 비영리법인이거나 고유번호를 부여받은 단체)** → 공급 성격에 따라 도서 저작권 인세·매절 대금 라인은 후보 케이스 `TX-09`를, 온라인 강의 R/S·비정기 약정금·개발지원금 라인은 후보 케이스 `TX-07`을 각각 `matrix_case_id`에 부여하되(11.1절 후보 케이스 보유 보류 원칙 준수), 판정 상태(`tax_decision_status`) \= `PENDING_REVIEW`로 격리하여 재무 담당자가 수익사업 영위 여부와 증빙 종류를 확정하기 전까지 마감을 차단합니다.
* **tax\_type\_cd \= 03 (부가가치세 과세특례자)** → 판정 보류. 현행 과세유형 체계에서 신규 발생이 드문 유형이므로 격리하고 담당자에게 알럿을 발송합니다.
* **매핑 불가 코드:** 판정 보류. 위 목록에 없는 tax\_type\_cd가 유입되면 격리하고 담당자에게 알럿을 발송합니다. 임의로 가장 유사한 유형에 매핑하지 않습니다.
* **공급 성격 우선 규칙:** 도서 재화를 공급하는 위탁자·매입처는 위 매핑으로 수취인 과세유형(payee\_tax\_type)을 설정하되, 매트릭스 케이스는 도서 재화 공급 면세(TX-11)로 고정합니다. 재화 공급은 수취인의 과세유형과 무관하게 도서 면세이므로, 과세유형 매핑 결과를 그대로 케이스에 연결하면 위탁자의 과세유형에 따라 도서에 부가가치세가 가산되는 오류가 발생합니다.
* **설계 유의:** TX-05와 TX-06의 구분이 API 응답 문자열로 직접 분기된다는 점이 이번 연동의 핵심 이점입니다. 당사가 4,800만 원 기준을 계산할 필요가 제거되며, 4,800만 원(부가가치세법 제36조 제1항 제2호 가목)과 1억 400만 원(제61조 제1항, 시행령 제109조 제1항)은 근거 조문 기록용으로만 보존합니다.

### **17.4. 1차 확인: 계약 체결 및 계약 원장 등록 시점 (필수 게이트)**

* **호출 시점:** [권리자 계약 원장, ADMN-INST-001]의 사업자 권리자 등록·수정 화면, 그리고 [도서 공급 원장, ADMN-BOOK-001]의 매입처 등록 화면에서 사업자등록번호 입력 직후 담당자가 [사업자 확인] 버튼을 누르면 진위확인 API를 호출합니다. 저장 버튼 클릭 시점에는 확인 결과 존재 여부만 검증합니다.
* **호출 항목:** 사업자등록번호(b\_no), 개업일자(start\_dt), 대표자성명(p\_nm)을 필수로 전송하고, 법인은 법인등록번호(corp\_no)를, 상호 검증이 필요한 경우 상호(b\_nm)를 함께 전송합니다. 미사용 항목은 빈 문자열로 포함시킵니다.
* **진위 불일치 시:** 저장을 차단하고 "국세청 등록 정보와 일치하지 않습니다. 사업자등록증의 사업자등록번호·대표자명·개업일자를 확인해 주세요"를 노출합니다. 불일치 항목을 추정하여 안내하지 않습니다(API가 어느 항목이 불일치하는지 반환하지 않기 때문입니다).
* **진위 일치 시:** 동일 응답에 포함된 상태 정보로 다음을 자동 채움 처리합니다. 수취인 과세유형(payee\_tax\_type), 세금계산서 발급 가능 여부(tax\_invoice\_eligible\_yn), 사업자 상태(business\_status), 최근 과세유형 전환일자(tax\_type\_change\_dt), 세금계산서 적용일자(invoice\_apply\_dt), API 최종 확인 시각(api\_checked\_at), API 응답 스냅샷(api\_response\_snapshot). 담당자는 이 값을 편집할 수 없습니다.
* **사업자등록증 교차 검증:** 담당자가 업로드한 사업자등록증의 과세유형 표기와 API 응답값이 불일치하면 저장을 차단합니다. 사업자등록증이 과거 유형으로 발급된 상태일 수 있으므로, 이 경우 API 응답값을 기준으로 정정된 사업자등록증 제출을 요청합니다.
* **상태 게이트:** 납세자 상태(b\_stt)가 폐업자이면 계약 원장 등록을 차단합니다. 휴업자이면 경고를 노출하고 재무 책임자 승인 후에만 저장을 허용하며, 승인 사유를 감사 로그에 기록합니다. 매입처와 위탁자도 동일하게 적용하며, 폐업 매입처에 대한 신규 발주를 차단합니다.
* **등록 화면 노출 형태:** 확인 결과 카드에 사업자등록번호, 상호, 대표자명, 납세자 상태, 과세유형, 최근 과세유형 전환일자, 세금계산서 적용일자, 조회일시를 표기하고, 원문 JSON은 접힘 영역에 보관합니다.
* **확인 결과 유효기간:** 확인 시점으로부터 90일(nts\_check\_validity\_days)을 유효기간으로 두고, 경과 후 계약 원장을 수정하거나 약정금 검수 승인을 시도하면 재확인을 요구합니다.
* **개인 프리랜서 및 자사 권리자:** 사업자등록번호가 없으므로 이 게이트를 적용하지 않습니다. 개인 권리자 등록 화면에는 확인 버튼을 노출하지 않습니다. 사업자등록 없는 개인 도서 공급자(TX-12)는 확인 자체가 불가하므로 원칙 차단 대상입니다.

### **17.5. 2차 확인: 정기 및 수시 재조회**

* **정기 일괄 재조회 (연 1회 핵심):** 매년 6월 15일부터 6월 30일 사이에 전체 사업자 권리자·위탁자·매입처를 대상으로 상태조회 API를 일괄 호출합니다. 국세청은 과세기간 개시 20일 전까지 과세유형 전환을 통지하며 전환 효력은 통상 7월 1일부터 발생하므로, 통지가 배포된 뒤 전환 시행 전에 조회하는 시점입니다. 다만 전환 효력일이 항상 7월 1일이라고 가정하지 않으며, 실제 효력일은 API 응답값으로 확정하고 값이 없으면 효력일 불명 상태로 분리합니다. 정기 조회·90일 유효기간은 내부 조회 정책으로 유지하되 법정 변경일 보장으로 쓰지 않으며, 조회 결과로 과세유형 버전 행을 사전 생성하되 효력일은 응답값으로 확정합니다.
* **정기 일괄 재조회 (분기):** 1월, 4월, 10월의 각 15일에 폐업·휴업 감지 목적으로 일괄 재조회합니다. 과세유형 전환 효력일은 API 응답값에 따라 달라질 수 있으므로 특정 일자로 고정하지 않고, 폐업은 수시로 발생하므로 감지 주기를 분리합니다.
* **수시 재조회 트리거:** 계약 갱신·수정 시, 약정금 검수 승인 시(제7장 7.2절 게이트), 증빙 승인 거부가 발생한 때, 도서 발주 등록 시, 위탁 계약 등록 시, 최종 확인일로부터 90일이 경과한 권리자의 정산 마감을 시도할 때 호출합니다.
* **과세유형 전환 감지 시 처리:** 응답의 과세유형 코드(tax\_type\_cd)가 원장 값과 다르면 자동으로 덮어쓰지 않고 변경 감지 목록([사업자등록 확인 이력, ADMN-SETT-008])에 적재하여 담당자 확인을 거칩니다. 확인 승인 시 기존 행에 종료일자를 설정하고 신규 유효일자 행을 Insert합니다. 유효 시작일자는 응답의 최근 과세유형 전환일자(tax\_type\_change\_dt) 또는 세금계산서 적용일자(invoice\_apply\_dt)를 사용하며, 값이 없으면 효력일 불명 상태로 분리하여 확인 대상으로 관리하며 7월 1일을 일괄 기본값으로 적용하지 않습니다.
* **전환 시점 이전 거래의 취급:** 과세유형 전환이 확인되어도 이미 마감된 월의 증빙과 세율은 정정하지 않습니다. 정산 엔진은 지급일(또는 공급시기)이 속한 유효일자 버전을 바인딩하므로 과거 월은 당시 유형이 유지됩니다.
* **간이에서 일반으로 전환된 경우의 경과 규칙:** 간이과세자가 일반과세자로 전환되는 경우에도, 전환을 통지받은 날이 속하는 과세기간까지는 간이과세자로 보는 경과 규정이 적용될 수 있습니다(부가가치세법 제62조 및 시행령 제110조). 시스템은 전환일자를 API 응답값에서 받아 적용하므로 이 경과 기간을 별도 계산하지 않습니다. 다만 권리자가 경과 규정을 주장하여 응답값과 다른 증빙을 발행하려는 경우, 담당자 확인 후 수동 조정 경로로 처리하고 근거를 기록합니다.
* **폐업 감지 시 처리:** 납세자 상태(b\_stt)가 폐업자로 확인되면 신규 증빙 발행 요청을 중단하고, 미승인 증빙의 리마인더를 중단합니다. 미지급 정산금은 강제 정산 트리거(제7장 7.3절)로 지급 실행 대상에 선정합니다. 지급 실행 대상 선정은 지급 성공·채무 소멸·세무 확정을 뜻하지 않으므로, 실제 지급 또는 적법한 상계·근거 있는 종결 전까지 미지급 잔액을 유지합니다. 폐업일자(end\_dt) 이후 공급분에 대한 증빙 처리는 재무 담당자 판단 대상으로 이관합니다. 위탁자·매입처가 폐업한 경우에도 수취 계산서 확보 가능 여부를 공급시기·폐업일·정정 사유로 먼저 판정하고, 확보가 불가한 경우에만 증빙불비 소명 절차로 전환합니다(제10장 10.4절 채널 4).
* **과세유형 전환 경계 판정:** 과세유형 전환일 직전·직후에 걸친 거래(예: 6월 말 지급, 7월 1일 전환)는 세무 판정 항목별 기준일을 적용합니다. 공급 성격·면세 요건·증빙 판정은 원공급의 공급시기에, 원천징수 발생·세율 판정은 실제 지급·적법한 상계·법정 지급 의제가 성립한 날에 유효한 사업자 유형 이력과 세무 규칙 버전을 연결합니다(11.3절 세무 버전 기준일 표와 동일 기준). 각 기준일의 API 응답 스냅샷을 판정 근거로 보존하되, 조회일과 효력일을 구분하여 기록합니다. 기준일의 과세유형을 확정할 수 없으면 판정 보류(PENDING\_REVIEW)로 분리합니다. API 응답은 판정 근거이지 모든 세무 항목의 기준일을 지급일로 통일하는 근거가 아닙니다.

### **17.6. 구현 규격**

* **배치 규격:** 1회 호출 최대 100건 제약에 맞추어 100건 단위로 청크 분할하여 순차 호출합니다. 청크 간 호출 간격을 설정값(국세청 배치 호출 간격(nts\_batch\_interval\_ms), 기본값 200ms)으로 두어 트래픽 제한에 대응합니다.
* **실패 처리:** 네트워크 오류 및 5xx 응답은 지수 백오프로 3회 재시도하고, 최종 실패 건은 재시도 큐에 적재하여 담당자에게 알럿을 발송합니다. API 장애가 정산 마감을 차단하지 않도록, 최종 확인일이 유효기간 내인 권리자는 기존 스냅샷 값으로 마감을 진행합니다.
* **신규 등록 경로:** 신규 계약 등록 시 API 조회가 최종 실패한 경우 등록을 보류 큐에 적재하고, 사업자등록증 등 수기 확인 증빙을 첨부한 임시 등록(PENDING\_VERIFICATION)만 허용합니다. 확인 대기(PENDING\_VERIFICATION)는 정기·수시 조회, 증빙 확인 및 허용된 승인 경로에서 확인이 완료되면 즉시 해제하며 다음 정기 재조회까지 기다리지 않습니다. 확인 경로·시각·증빙·승인자·응답을 기록하고, 확인 완료 전까지 마감·지급 대상에서 제외합니다.
* **서비스키 관리:** 서비스 키(serviceKey)는 3.2절의 자격 증명 저장소에서 관리하며 소스 코드·설정 파일·로그에 평문으로 기록하지 않습니다. 호출 로그에 기록할 때는 키를 마스킹합니다.
* **트래픽 한도:** 공공데이터포털은 활용신청 시 개발계정·운영계정별 일일 트래픽 한도를 부여합니다. 정기 일괄 재조회 예상 호출량이 한도를 넘지 않는지 활용신청 단계에서 확인하고, 초과 시 운영계정 증량을 신청합니다. 조회 대상에 매입처·위탁자가 추가되어 호출량이 증가하는 점을 산정에 반영합니다. 구체적 한도 수치는 활용신청 승인 화면에서 확인해야 하는 값이므로 본 문서에 기재하지 않습니다.
* **이력 테이블:** 국세청 사업자등록 확인 이력(nts\_verification\_log) 테이블 (컬럼: 로그 식별자(log\_id), 대상 구분(subject\_type: RIGHTS\_HOLDER / CONSIGNOR / SUPPLIER), 대상 식별자(subject\_id), 계약 식별자(contract\_id), API 유형(api\_type: VALIDATE / STATUS), 사업자등록번호(b\_no), 요청 데이터(request\_payload), 응답 데이터(response\_payload), 사업자 상태 명칭(b\_stt), 사업자 상태 코드(b\_stt\_cd), 과세유형 명칭(tax\_type), 과세유형 코드(tax\_type\_cd), 최근 과세유형 전환일자(tax\_type\_change\_dt), 세금계산서 적용일자(invoice\_apply\_dt), 폐업일자(end\_dt), 일치 여부(match\_result), 확인일시(checked\_at), 확인자(checked\_by), 트리거 종류(trigger\_type: CONTRACT\_REG / PERIODIC / AD\_HOC / MILESTONE\_APPROVAL / PURCHASE\_ORDER / CONSIGNMENT\_REG)). 응답 원문을 그대로 보존하여 사후 소명 자료로 사용합니다.
* **보존 기간:** 조회 이력은 계약 관련 중요서류에 준하여 계층 2(제3장 3.5절) 보존 정책을 적용합니다. 대표자명이 포함되므로 개인정보 파기 정책의 필드 매핑(pii\_destruction\_field\_map)에 대표자명 항목을 포함시킵니다.
* **감사 로그 연동:** 조회 실행, 과세유형 변경 승인, 휴업자 승인 저장, 폐업 감지에 따른 강제 정산 실행을 시스템 감사 로그(ADMN-CONF-010)에 기록합니다.

### **17.7. ADMN-SETT-008(목록) 화면 규격**

* **목록 탭 1 (조회 이력):** 대상 구분(권리자 / 위탁자 / 매입처), 대상명, 사업자등록번호(마스킹), API 종류, 납세자 상태, 과세유형, 일치 여부, 조회 트리거, 조회일시, 조회자. 필터는 기간, 대상 구분, 상태, 과세유형, 일치 여부, 트리거 종류입니다.
* **목록 탭 2 (과세유형 변경 감지):** 대상명, 원장 과세유형, API 과세유형, 전환일자, 세금계산서 적용일자, 확인 상태(미확인 / 승인 / 보류). 승인 시 유효일자 버전 행이 생성됩니다.
* **목록 탭 3 (폐업·휴업 감지):** 대상명, 대상 구분, 상태, 폐업일자, 미지급 정산금 잔액, 미승인 증빙 건수, 미수취 계산서 건수, 후속 처리 상태.
* **목록 탭 4 (조회 실패 재시도 큐):** 대상명, 실패 시각, 오류 코드, 재시도 횟수, 수동 재시도 버튼.
